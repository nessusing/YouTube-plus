## P2 凭证缓存

**现状**：`generate()` 和 `deleteConversation()` 各自先 GET 一次 `/u/N/app`，每批 4 个请求，其中 2 次是抓页面。浪费的是 HTTP 请求，不是 Gemini 额度；但增加延迟，流量也更像机器。

**改法**：
- 把 `at` / `bl` / `sid` 按账号 N 缓存几分钟，改 N 时清掉。
- 遇到 400 / 405 时清缓存、重抓、重试一次；还失败就按现有的错误映射处理。
- 自检和「我已登录」检测（design.md §15.1）仍然实时抓，不走缓存。
- 一起缓存 `processSession` 的 API key `d2zJAe`（同一个页面里，跟登录状态无关，很少变；design.md §10.8）。

跟走哪条通道无关：缓存只管凭证从哪来、什么时候刷新。两条通道和删对话都用这组凭证。

**进度**
- 2026-11-20：定下改法，决定先不做。

## P3 官方 Gemini API Provider

**想要什么**：`StreamGenerate` 下线时 TL;DR 不至于整个失效。

**做法**：实现 `SummaryProvider`（design.md §9.1）。用户在设置里填 AI Studio 的免费 key，直接把 YouTube URL 交给模型。

**好处**：有文档；没有封号风险；不需要 YouTube 应用和活动记录，也不用删对话。
**代价**：用户要自己填 key，不再是零配置，但仍然免费。

**跟网页通道的关系**：原来打算当 `StreamGenerate` 下线时唯一的后备。2026-11-21 `processSession` 已经实现（design.md §10.8），两条网页通道互为后备，这一条往后放。仍然有价值：两条都是内部接口，以后照样可能变；也不受个性化设置影响（design.md §45）。

**进度**
- 2026-11-21：P4（现 design.md §10.8）原型证明 YouTube 应用在新协议下能用，P3 往后放。
- 2026-11-21：优先级改为看 P4 原型的结果再定。

## P16 一个视频被拒，整批都失败

**现象**（日志）：2026-11-20 20:21–20:22，连续 3 批回答都是「违反政策」的拒绝，三批里都有 `0rEfO0pShEU`。一个视频被拒，整批 5 个都记成「答案里缺了」的 `transient`；重试时它又被分进下一批，把别的视频一起拖下水。2026-11-20 01:03 还有一批回答「I'm having a hard time fulfilling your request」，可能是同类问题。

**改法**：整批没解析出任何结果时，拆成单个视频重试一次；单个也被拒的视频标成不能总结（不再算 `transient`），不再进批。

**进度**
- 2026-11-21：从日志里发现，记下。

## P17 批量回答像 JSON 却没解析出来

**现象**（日志）：2026-11-21 01:15 一批，回答开头是正常的 JSON 数组（`"id"`、`"status":"ok"` 都在），结果 5 个全记成「答案里缺了」。日志只记了前 500 个字符，看不出是被截断、转义有问题还是后面多了东西。同一批要求中文，`points` 却是英文（`lang` 写的是 `zh`）。

另外 2026-11-20 12:26 有两次 `no answer text in 136 bytes`（`protocol`），也是没留下原文。

**下一步**：解析失败时把完整回答记进日志（只记模型的回答，不记请求），下次出现就能看到原因；再看 `parseBatch` 要不要更宽松。语言不对的问题等有更多例子再看。

**测个性化设置时（design.md §45）抓到的两种**（网页 UI，7 次里各 1 次）：
- **数组输出两遍**：`[...][...]`，中间没别的。`parseBatch` 的 `\[[\s\S]*\]` 从第一个 `[` 匹配到最后一个 `]`，解析失败，整批记成「缺了」。很可能就是上面 01:15 那一批。改法：整段解析失败时，从头按括号配对取出第一个完整的数组再解析。
- **JSON 本身写坏**：某个对象里出现 `"lang":"zh","yue",`，整段不合法。改法：数组解析失败时退一步逐个对象解析（按括号配对切出每个 `{...}`），坏的那一个算缺，其他照常用。

**进度**
- 2026-11-21：`parseBatch` / `parseSummary` 改成按括号配对（跳过字符串里的括号）：取第一个由对象组成的数组；整段不合法时逐个对象解析，坏的算缺。补了单元测试。
- 2026-11-21：测个性化设置（design.md §45）时复现了两种原因，定下改法。
- 2026-11-21：从日志里发现，记下。

## P23 扩展语言跟随 YouTube，TL;DR 按视频语言

依据 design.md §2「贴合官网」：语言不让用户在扩展里另设，界面跟 YouTube 走，TL;DR 跟视频走。

### 扩展语言 = YouTube 的界面语言

设置页的语言选项去掉。设置页、缩略图上的提示、日志等所有扩展界面，都用用户在 YouTube 上设的语言。

- **从哪读**：首选 `<html lang>`，普通 content script 直接读 DOM。读不到时看 cookie `PREF` 里的 `hl=`（`ytcfg` 要在页面 JS 环境里读，没用）。各种语言下的具体值要实测（例如简体中文是 `zh-CN` 还是 `zh-Hans-CN`）。
- **映射**：`zh*` → 中文，其他一律 → English（扩展只有这两种）。繁体（`zh-TW` / `zh-HK`）先当中文；以后有需要再加繁体。
- **存**：每次打开 YouTube 页面读一次，跟存着的不一样就写进 `settings.lang`。现有的 `initLang` 监听会让各处跟着切换。用户在 YouTube 上改语言后页面会重新加载，所以能读到新值。
- **没打开过 YouTube 时**（刚装完就打开设置页）：沿用现在的 `detectLang()`，按浏览器语言；打开 YouTube 后自动改过来。
- **设置页**：「通用」里的语言一栏整个删掉，`opt.language` / `opt.languageHint` 文案一起删。
- **代价**：YouTube 用英文、扩展想用中文的组合做不到。不留手动覆盖。

### TL;DR 默认用视频自己的语言，由 Gemini 判断

视频说什么语言就写什么语言，**任何语言都一样**：中文写中文（简体视频写简体），英文写英文，越南语写越南语。跟扩展语言无关。（原先定的「中英以外用扩展语言」2026-11-21 取消。）

**为什么交给 Gemini**：三个取语言的办法比较过：

| 办法 | 怎么拿 | 问题 |
|---|---|---|
| 视频元数据 | 缩略图所在的 feed 数据里没有语言。观看页的 player 响应里有：自动字幕轨（`kind: "asr"`）的 `languageCode` 就是说话的语言；多音轨视频还有 `audioTracks`，原声轨有标记。官方 Data API 的 `snippet.defaultAudioLanguage` 要 key，且是上传者自己填的，经常空着 | 预生成时每个视频要多请求一次 player，请求量翻倍；关了字幕或音乐视频没有自动字幕轨 |
| 按标题判断 | 扩展自带 `browser.i18n.detectLanguage(title)`（离线 CLD），不花请求 | 标题短，常中英混写；中文标题配英文讲解很常见；YouTube 会给部分用户显示**自动翻译后的标题**，判断的是翻译不是原文 |
| 让 Gemini 判断 | prompt 里写明规则 | 几乎没有：Gemini 本来就读了字幕，最清楚视频是什么语言 |

前两个办法都不做。

**改法**：
- **prompt**（`protocol.ts` 的 `rules()`）：「用视频主要说的语言写，不翻译；中文按视频用的简体或繁体，分不清用简体」；`titleMatch.reason` 用同一种语言。批量 prompt 里每个视频各按各的语言，规则写一次即可。`SummaryInput` 不再带语言。
- **返回**：schema 里已有 `"lang":"<language code>"`，改为让 Gemini 填它判断出的视频语言，存进缓存，tooltip 和日志可以用。P17 里出现过 `lang` 写 `zh`、内容却是英文，所以 `lang` 只作参考，不拿它做逻辑判断。
- **缓存**：内容跟扩展语言无关了，key 改成 `tldr/cache/orig:<videoId>`；旧的 `<en|zh>:<videoId>` 在整理缓存时删掉（升级后所有视频重新生成一次）。切扩展语言不再重新生成。
- **自检**：自检用的 `jNQXAC9IVRw` 是英文视频，扩展语言是中文时也应该返回英文，顺便验证 prompt 生效。

**还差**：
- 手测：YouTube 设中文 / 英文时扩展界面跟着切；中文、英文、其他语言的视频各看几个 TL;DR；`<html lang>` 实际取值。
- e2e：`fixtures.ts` 把 `settings.lang` 设成 `en`，现在打开 YouTube 会被 YouTube 的语言覆盖。e2e 账号的 YouTube 界面要是英文，或者改成在 YouTube 上设语言。

**进度**
- 2026-11-21：实现。TL;DR 规则改为任何语言都跟视频走；设置页的语言选项删掉；新增 `lang.content.ts` 同步 YouTube 语言；缓存 key 去掉扩展语言。
- 2026-11-21：扩展语言改为跟随 YouTube，设置页的语言选项整个去掉；TL;DR 默认用视频语言，由 Gemini 判断，中英以外的用扩展语言。

## P11 迷你播放器面板偶尔缺刚加的视频

原 `queue-test-findings.md` 的 F12。

- **场景**：播放列表模式，迷你播放器在放单个视频，点「加入 <列表名>」。
- **预期**：迷你播放器下面出现列表：当前视频 + 列表原有条目 + 刚加的视频（「1 / 4」）。
- **实际**：完整跑一遍 L4 时出现过一次，面板只有「1 / 3」，缺刚加的那个；顶栏数字是对的。单独连跑 6 次都正常。
- **推测原因**：`syncList()` 用 `next` 读列表，读不到新视频时在 1.5、3、5 秒后再读，最后一次不管满不满足都用（design.md §24.8）。如果 `next` 落后超过约 9.5 秒，面板就缺这一条，之后也不会再补。
- **测试**：`queue-panel.spec.ts` › playlist mode, a single video in the miniplayer…；`modes.spec.ts` › ② single video in the miniplayer…（按正确结果断言，偶尔会失败）。
- **如果经常出现**：最后一次读取仍不满足时，过一会儿再补一次 `syncList`；或者等面板派发的 `yt-playlist-data-updated` 再核对一次。

**进度**
- 2026-11-21：L4 里出现一次，先观察。

# 新功能

## P13 评论弹幕

> 设计已讨论定稿（2026-11-21）；实测 1、2 已做（2026-11-22，见「实测结果」）；观看页已接通（见「进度」）。**开发在分支 `p13-danmaku` 上进行，不在 master 上。**
> 参考 ComVi（CHI 2026，arXiv 2603.26173）：借用它的阅读时长、赞数归一化和「同一时间只显示一条」的排期；不照搬它看画面、用全部评论的做法。

**一句话**：评论以字幕卡的形式出现在播放器底部，一次一条。带时间戳的评论在那个时间点出现；其余的用本地算法按热度撒到全片，或者由 Gemini 读字幕后放到相关的时刻。

**范围**
- 只在 `www.youtube.com/watch` 生效。嵌入播放器、youtube-nocookie、music.youtube.com 都不管。
- 只在普通模式（包括置顶）、影院模式、全屏里显示；迷你播放器里不显示（包括 §44 的标题栏状态）。
- 不做：直播和直播回放（已有聊天回放）、Shorts。
- AI 只走 Gemini，不内置本地模型；不让 AI 看画面（太慢），只靠字幕和评论文字。

**开关**
- 设置页一个全局开关，默认关。关掉时：没有按钮，不拉评论，不调 Gemini。
- 全局开时，播放器控件栏右侧（字幕按钮旁边）一个开关按钮，像字幕按钮一样记住状态，对所有视频生效。按钮关着时什么都不跑。
- 按钮图标自己画（不用 YouTube 的），风格和官方控件一致，画好给用户看再定。状态：

| 状态 | 样子 |
|---|---|
| 关 | 空心 |
| 开，AI 还在处理 | 实心，旁边一个小点在闪 |
| 开，处理完成 | 实心 |
| 开，但降级了 | 实心，tooltip 写明原因 |
| 没有评论 / 评论区关闭 | 灰色，tooltip 写「此视频没有评论」 |

- 不加快捷键。

**什么时候处理**
- 只在打开观看页、弹幕开关开着时处理。v1 不给队列里或缩略图上的视频提前生成。
- 切到别的视频（包括自动播放下一个）时：立刻停止拉旧视频的评论；已经发出去的 Gemini 请求让它跑完，结果写进缓存；还没发出去的批次取消。

**拉评论**
- 在 MAIN world 直接调 InnerTube `next`（复用 `queue/innertube.ts` 的 `prepare()` 签名），不滚动页面，不动评论区 DOM：先用 videoId 调一次，拿到评论区的 continuation token，再一页一页往下翻。每页约 20 条，只能串行。
- 默认排序是「热门评论」，前面的就是最值得显示的，所以不全拿。
- 边拉边处理：拉到前 100 条就开始处理，后台继续拉。拉取上限 = max(200 条, 每分钟 15 条)，封顶 300 条（实测：「热门」排序约 300 条以后混进大量 0–1 赞的新评论）。
- 只用一级评论。回复不拿，但**回复数**（一级评论里自带）算进热度。用户对这一条有保留，之后要继续实验（比如在卡片里带上赞最多的那条回复）。ComVi 论文里没提回复。
- 评论一视同仁：不按语言筛选，置顶评论和作者评论不加权、不加标记。

**本地过滤**（不送给 Gemini，也不显示）
- 纯表情、太短的、重复的（只留赞最多的一条）、带链接的。
- 「太短」按文字算：中日韩文字一个算 3 个拉丁字母（实测：只数字符会把一半中文评论滤掉）。

**带时间戳的评论**
- YouTube 已经解析好时间戳（`commandRuns` 里的 `watchEndpoint.startTimeSeconds`），直接用。
- 每个时间戳都出现一次，每次都显示整条评论。排期时每次出现各算一个独立的排期项。超出视频时长的时间戳忽略。
- **真目录**：第一个时间戳是 0:00、时间戳有 5 个以上、每行只是「时间 + 短标题」。这种只在 0:00 整条显示一次，当作「本视频目录」。高光合集（时间戳多，但不符合这些条件）照上一条的规则，每个时间戳都显示整条。
- 带时间戳的评论优先占位。那个时刻被占了时只能往后推（最多 5 秒），推不进去就放弃这条，不提前、不改成 ambient，免得剧透。

**同一时刻的多条评论**
- 落在 ±2 秒内的算同一时刻，放进同一张卡，按赞数轮流显示，角上标「1/3」；最多轮播 3 条，超过的标「1/3 +4」。
- 每条照常按显示时长计时。整体可以往后推，最多推到轮播完，不受「最多推 5 秒」的限制。

**定位方式**：设置里全局选「本地」或「AI」，默认本地。切换后，当前视频马上按新方式重排。两种方式的结果都缓存；切回 AI 时如果已有缓存，就不再调 Gemini。

**本地模式**（不调 Gemini）
- 热度 = 赞数权重 × 赞数（Box-Cox 变换后归一化） + 回复权重 × 回复数（取 log 后归一化） + 新旧权重 × 新旧（默认越新越优先，权重小；设成负数就是越旧越优先）。「新旧」用 InnerTube 的「3 周前」这类文字换算成天数。
- 每分钟条数 = 1 + log₁₀(总评论数)，夹在 1 到 6 之间；总条数 = 每分钟条数 × 分钟数，不超过拿到的评论数。总评论数取评论区表头里的数字。
- 怎么撒：
  1. 把视频切成 30 秒的窗口；
  2. 每个窗口的名额按 `1 + 热度权重 × 该窗口的「最常重播」热度` 分配（热度曲线在 `next` 响应里，只有播放量够高的视频才有；没有就均匀分配）；
  3. 按热度从高到低轮流分到各个窗口，避免高赞评论都挤在开头；
  4. 窗口内的具体位置加随机偏移，随机数用 videoId 当种子，同一个视频每次结果都一样；
  5. 开头 5 秒不放。
- 防剧透：评论里出现「结尾」「最后」「反转」「ending」「twist」「the end」这类词的，只放在视频的最后 20%。词表和比例都可调。

**AI 模式**（Gemini）
- 走 TL;DR 现有的通道和 YouTube 应用：一次请求给视频链接和一批评论（约 100 条），让它读字幕后给每条评论定位。不单独做「事件时间线」那一步。
- 输出用紧凑格式，每条一行，不要 JSON，不要理由：
  - `id|秒|置信度`：定位到具体时刻；
  - `id|a`：ambient，对不上具体时刻；
  - `id|x`：不适合显示（广告、引流、骂人、跟视频无关）。
- 只用高置信度（≥ 0.9）的时间：放到给出的时间。中、低置信度的，和超出视频时长的，都当 ambient（实测：≥ 0.9 的误差都在 5 秒以内，0.5–0.8 的误差 2–359 秒，连段落都不准）。
- prompt 里写明每档置信度的含义、「拿不准就用 `a`」、`x` 只给广告 / 引流 / 骂人 / 无关（实测第二版，见「实测结果」）。
- AI 定位的评论每条只出现一次。
- ambient 只从 Gemini 判成 `a`、置信度不够高、时间超出视频的评论里挑，用来填空：时间轴上空闲超过 20 秒就补一条，按热度挑，按「最常重播」曲线加权。实测效果不好就去掉。
- 分层上屏：
  - 0 秒：只显示带时间戳的评论。AI 结果回来之前不撒 ambient，因为 AI 还没看过的评论可能是剧透；
  - Gemini 每批结果回来后，只改写还没播到的部分，已经显示过的评论不再排进去；
  - 再次打开同一个视频时，直接读缓存。
- 一批失败了（超时、解析不出来、被拒）：稍后重试一次；还失败就拆成两半各试一次；最后还失败的评论算「未知」，不当 ambient，也不显示。
- Gemini 用不了时（没登录、熔断中、额度用完、没字幕、一批最终失败）不弹提示，按设置处理：
  - 「退回本地模式」（默认）：这个视频改用本地模式的分布，按钮 tooltip 写「已退回本地模式：原因」；
  - 「只显示带时间戳的评论」：方便测试对比。
- 额度（v1）：和 TL;DR 共用同一个串行队列、熔断、每小时 / 每天的上限；弹幕请求的优先级等同「点击」，排在预生成的 TL;DR 前面。测试期间可以用 `features.tldr` 关掉 TL;DR 省额度。以后要不要单独设上限、在设置里怎么和 TL;DR 关联，用过再定。个性化设置（design.md §45）和 P16、P17 的问题这里也会碰到。
- 不需要自己拿字幕：Gemini 在 YouTube 应用里自己读。TL;DR 也拿不到字幕原文（回答里只有总结），所以没法「存下来复用」。只有在 YouTube 应用给的时间太不准时，才考虑在观看页自己拿字幕贴进 prompt（见 P5），字幕只跟着弹幕缓存。

**排期**（纯本地，0.5 秒精度）
- 评论长度不设上限，长的靠滚动显示完。
- 显示时长：
  - 两行以内：按字数算，每字符时长为拉丁字母 0.068 秒、中日韩文字约 0.2 秒，最长 5 秒；
  - 超过两行：每两行算一屏，每屏 5 秒，然后往下滚到下一屏；总时长 = 屏数 × 5 秒。
- 行数跟播放器宽度和字号有关（全屏和普通模式不一样）：排期时按字数和一个参考行宽估算；实际显示时按真实行数分屏，在分到的时长里滚完。
- 两条评论之间至少空 0.5 秒；评论少时间隔自然拉长，不硬凑。
- AI 模式打分 = 2 × 相关度 + 1 × 热度 × 显示时长（热度同本地模式；相关度由置信度换算）。同一时间只显示一条，前一条显示完、再空出间隔才出下一条；用动态规划求总分最高。

**显示**
- 盖在 `#movie_player` 上的一层，`pointer-events: none`。
- 底部居中的字幕卡，样式仿官方字幕：半透明深色圆角底（pill），白字。开头显示 `@handle`，不显示头像和赞数。
- 原文不改：会员表情显示成和文字一样高的行内小图；@提及、#话题照原文显示，不能点。
- 淡入、淡出各约 200–300 ms。
- 一条最多显示 2 行；超过时每屏停 5 秒，再滚到下一屏（见「排期」）。
- 字号跟着播放器大小变，像官方字幕一样。
- 避让：控件栏出现时整体上移；开着字幕时放在字幕上方（实时量字幕框的位置，因为用户可以拖动字幕）。
- 播放控制（和主流弹幕播放器一致：时间轴固定，绑在视频时间上）：
  - 暂停时卡片停住，计时也停；
  - 往回拖时，同一位置重放同样的评论；
  - 拖进度条时清空，从新位置开始；如果落在一张卡的中间、剩下的时间还有 1.5 秒以上，就立刻显示这张卡，直接从对应的那一屏开始；
  - 倍速播放时按视频时间走；
  - 播广告时（`#movie_player.ad-showing`）隐藏，正片继续后接着播。

**缓存**
- 按 videoId 缓存评论、Gemini 定位结果和本地分布，有效期 7 天，单独占一块存储（默认 2 MB，满了按 LRU 淘汰），不和 TL;DR 抢地方。
- 过期后重新拉评论，只把新出现的评论送给 Gemini，已经定位过的直接沿用。

**调试和自检**
- 设置页的调试开关：打开后，卡片角上标出这条评论的来源（`时间戳` / `AI 0.8` / `ambient` / `本地`）；各环节耗时也显示在按钮的 tooltip 里。
- 日志：Gemini 的完整原始回答一律记下（吸取 P17 的教训）。每个视频记一行耗时：拉评论用了多久、拉了几页几条；每批 Gemini 用了多久；从打开视频到第一条 AI 结果、到全部完成各用了多久；有没有退回本地模式。
- 自检加一项「弹幕」：用一个固定的公开视频，试拉一页评论并解析成功。不试 Gemini 定位，因为 TL;DR 的自检已经验证过 Gemini 通道。

**开发期间的可调参数**
- 开发期间，设置页里尽量多放可以手调的参数，方便边看边调。实测稳定后再决定哪些留给普通用户、哪些收起来或删掉。
- 至少包括：
  - **显示**：每屏秒数（5）、每字符时长（拉丁字母 / 中日韩文字）、最短间隔（0.5 秒）、淡入淡出时长、字号比例、底色透明度、参考行宽、拖动后补显示的剩余秒数阈值（1.5）；
  - **评论**：首批条数（100）、拉取上限（200 条 / 每分钟 15 条 / 封顶 300）、太短的字数阈值；
  - **带时间戳的评论**：最多往后推的秒数（5）、同一时刻的窗口（±2 秒）、轮播条数（3）、真目录的判定条件（0:00 开头、时间戳个数 5、标题长度）；
  - **热度**：赞数权重、回复权重、新旧权重（可以是负数）；
  - **本地模式**：每分钟条数公式的常数和上下限（1 / 6）、窗口长度（30 秒）、「最常重播」权重（0 = 关）、开头空白（5 秒）、防剧透词表和放置比例（最后 20%）；
  - **AI 模式**：给 Gemini 的提示词（整段可编辑，带「恢复默认」；评论列表、视频链接、标题、时长用占位符填入；用户会审查和微调）、每批条数（100）、高置信度的分界（0.9）、相关度权重（2）、热度权重（1）、ambient 开关和空闲阈值（20 秒）、用不了时的行为（退回本地 / 只显示带时间戳的）；
  - **缓存**：有效期（7 天）、存储上限（2 MB）。

**测试**
- 纯函数写单元测试：评论解析、时间戳提取、目录识别、过滤、显示时长、本地分布、同一时刻聚类、动态规划排期、Gemini 输出解析。
- 卡片显示、避让控件栏和字幕、各种播放器模式：手测，最后再补 L4 自动化。单元测试开发时自己跑；`npm run test:all` 由用户手动跑。

**后备方案**：如果实测下来整套流程不够快（用上面的耗时日志判断），改成只给播放列表队列里的视频提前生成，这样至少能预知接下来要看哪几个视频，提前缓存好。

**要实测的**
1. 直接调 `next` 拉评论：continuation token 在哪；评论数据的格式（是不是在 `frameworkUpdates` 的 `commentEntityPayload` 里）；赞数是不是「1.2K」这种缩写；回复数和发布时间在哪；每页多少条、多快；会不会被限流。「最常重播」热度曲线在响应里的位置。
2. YouTube 应用能不能给出准确到秒的时间（先在 gemini.google.com 手动问几个视频）；100 条评论一批要多久；会不会老老实实按紧凑格式输出。
3. 盖上这一层以后，官方的悬停显示控件栏、双击全屏有没有受影响；能不能可靠拿到字幕框的位置。

**实测结果**（2026-11-22）

1. 拉评论（`next`）：
   - 第一次用 videoId 调：评论区是 `contents.twoColumnWatchNextResults.results.results.contents[]` 里 `sectionIdentifier === 'comment-item-section'` 的 `itemSectionRenderer`，它的 `contents[0].continuationItemRenderer.continuationEndpoint.continuationCommand.token` 就是第一页。`engagementPanels[0]` 的排序菜单里有「Top / Newest」两个 token，用不上。
   - 往后翻：`onResponseReceivedEndpoints[*].*.continuationItems` 最后一项的 `continuationItemRenderer`（`continuationEndpoint` 或 `button.buttonRenderer.command`）里是下一页的 token。第一页里还有 `commentsHeaderRenderer`：`countText` 是精确总数（「2,462,497 Comments」）。
   - 评论在 `frameworkUpdates.entityBatchUpdate.mutations[].payload.commentEntityPayload`，每页 20 条：`properties.commentId / content.content / publishedTime（「3 months ago」「(edited)」）/ replyLevel`，`author.displayName`（@handle）、`author.isCreator`，`toolbar.likeCountNotliked`（缩写）、`toolbar.replyCount`（0 时是空串）。
   - 数字格式跟着 `context.client.hl` 变：en-GB「9.3k」、en「9.3K」、zh-CN「29万」、de 给精确数「294.069」。**请求时固定 `hl: 'en'`**，只需解析 K / M / B；`publishedTime` 也是英文。
   - 时间戳在 `content.commandRuns[].onTap.innertubeCommand.watchEndpoint`（`startIndex` / `length` 指向原文）。要核对 `videoId` 是当前视频（也可能链到别的视频）。**`0:00` 没有 `startTimeSeconds` 字段**，缺省当 0。会员表情在 `attachmentRuns`，粗体在 `styleRuns`。
   - 「最常重播」：`frameworkUpdates…macroMarkersListEntity.markersList`，`markerType: MARKER_TYPE_HEATMAP`，100 段 `{startMillis, durationMillis, intensityScoreNormalized}`。
   - 速度：第一次调用约 0.8 秒（响应 780 KB）；之后每页 250–500 ms、约 580 KB。600 条（30 页）串行 11.7 秒，没被限流。不登录（匿名调用）也能拿到同样的数据。
   - 「热门」排序拉到约 300 条以后开始混进 0–1 赞的新评论，后面的价值很低。
2. Gemini 定位（YouTube 应用）：用带时间戳的评论当标准答案，去掉时间戳后和其他评论混成 100 条，让它定位。视频 E7uGvsT_nnM（13 分钟），32 条有标准答案。
   - 速度和格式：100 条约 8–10 秒；完全按 `id|秒|置信度` 输出，100 行一行不少（`x` 后面偶尔多带一个置信度，解析时忽略）。
   - 第一版 prompt（只说「置信度 0–1」）：置信度全在 0.7–0.95，没有区分度；中位误差 5 秒，但有 366、159、119 秒这种离谱的；68 条没时间戳的评论有 57 条被给了具体时间，只有 5 条判 `a`；`x` 被用在了跟画面有关的玩笑上。
   - 第二版 prompt（定义每档置信度的含义、「拿不准就用 a」、`x` 只给广告 / 引流 / 骂人 / 无关）：**置信度 ≥ 0.9 的 12 条误差全在 5 秒以内**；0.5–0.8 的 12 条误差 2–359 秒，基本不可用。`a` 增加到 10 条，`x` 降到 1 条，但多数评论仍被给了时间。还出现一个超出视频时长的时间（854 秒，视频 788 秒）。
   - 中文视频（第二版 prompt，另加一句「视频长 N 秒，时间都在 0 到 N 之间」）：
     - **很多中文频道没有字幕轨**，连自动字幕都没有（老高、小Lin、Linvo 抽查的几个都没有；影视飓风、何同学有）。没字幕的 Gemini 直接回 `no_transcript`（老高《意识》），只能退回本地模式。
     - 中文评论很少带时间戳：抽查的 20 多个视频里，前 200–300 条中只有 0–14 条。
     - 何同学 -tHdM8dOeAc（12 分钟）：12 条有标准答案。**没有一条给到 ≥ 0.9**，按 0.9 的分界一条都不会放到具体时间；49 条判 `a`。这个视频的评论多是对画面、配乐、梗的反应，字幕里没有对应的话。0.85 的 3 条看上去是对的（误差约 1–7 秒，对照同一场景的标准答案）；0.5–0.8 的同样不可靠（误差 117、260 秒）。高置信度的分界先定 0.9，可调，以后视频多了再看要不要降到 0.85。
     - 没再出现超出时长的时间（样本小，不能确定是那句话起的作用；解析时照样把超出时长的当 ambient）。
   - 「太短」的阈值要按文字算：12 个字符的阈值把一半中文评论滤掉了。中日韩文字按 3 个拉丁字母算以后，196 条里留下 176 条。
   - 测试对话留在 Gemini 里：`/app/0db1d17598b5234a`（英文，第一版）、`/app/faedcf8cdec9d3f1`（英文，第二版）、`/app/dfae8bc08115018e`（老高，`no_transcript`）、`/app/0f6c3c210f8b6d59`（何同学）。

**进度**
- 2026-11-22：观看页接通，在 Chrome 里试过（英文 E7uGvsT_nnM、中文 wraBVnAfunc）：
  - MAIN world（`danmaku-main.content.ts`、`main-world.ts`）调 `next`，固定 `hl: 'en'`，没登录时不签名照样调（`innertube.ts` 的 `prepare()` 加了 `anonymous`），在页面里解析完只把结果传过来。视频信息取 `#movie_player.getPlayerResponse().videoDetails`（时长、标题、`isLiveContent`）。
  - `session.ts`：一个视频一个会话。拉到 `firstBatch` 条先排一次，之后边拉边重排；`mergeTimeline` 只改还没开始的卡片（已经开始的留着，往回拖能重放；新的避开它们，不重复已显示过的评论）。英文 13 分钟拉 200 条，中文长视频拉 300 条。
  - AI 模式：请求走 TL;DR 服务的同一个队列（`TldrService.ask()`，排在所有 TL;DR 前面，像点击一样不受上限约束，但受熔断约束，算进计数），后台把 Gemini 的完整回答记进日志。每批失败按设计重试、拆半；`no_transcript`、没登录、额度、风控算整个视频用不了，按设置退回。实测：英文视频首批回来后从 15 张卡变成 45 张；老高的视频回 `no_transcript`，退回本地模式，提示写明原因。存的是 Gemini 的原始判断，置信度分界改了以后对缓存也生效（`withCutoff`）。

## P22 发弹幕

> 二期，在 P13 之后做。还没讨论交互细节。

**一句话**：模仿原生支持弹幕的平台，让用户在播放时写弹幕。写的弹幕作为一条公开的 YouTube 评论发出去，用自己的账号。

**已定**
- 发送时自动在开头加上当前播放时间，比如「2:35 这里太绝了」。这样它就是一条带时间戳的评论：装了扩展的人在 2:35 能看到它（走 P13 带时间戳评论的规则）；没装的人看到的是一条普通评论，YouTube 会把时间显示成可以点的链接。
- 发出后立刻在本地显示，不等 YouTube 回读。
- 本地限速：默认每分钟最多 2 条，可调。

**风险**
- 发出去的是公开评论，所有人都能看到，用的是用户自己的账号。
- 像 B 站那样频繁发，YouTube 可能把评论扣下审核、隐藏，严重的可能限制账号。这就是要限速的原因。

**开工时再定**：输入框放在哪；全屏时怎么输入；发送失败怎么处理；要不要先预览再发。
