# 第一部分　共用

## 2. 原则

自用（未打包加载），但按能上架的标准写；零成本（用浏览器已登录的账号，不用 API key / OAuth）；每个功能单独开关、互相隔离；WXT + TypeScript + 原生 DOM / Shadow DOM。

**贴合官网**：扩展紧跟 YouTube 官网的数据、模式、体验和用户习惯。能从官网拿到的（账号、播放列表、用户设的语言等）就直接用，不在扩展里另存一份，也不让用户再设一遍；界面、控件、交互仿照官网，让人感觉是 YouTube 自带的功能。

**开发和测试时静音**：开发、调试、测试时打开的视频一律静音：自动测试、Claude in Chrome 操控的真实 Chrome，以及其他任何会打开视频的地方都一样。能在浏览器层面静音的就在浏览器层面做（e2e 启动参数 `--mute-audio`，见 `tests/e2e/support/env.ts`；手动可以给标签页静音），不改播放器自己的音量和静音状态；做不到时再让页面里的视频静音（`video.muted = true`）。

扩展图标用 `docs/icon-drafts/d.svg`。红色播放键取自 YouTube 商标，**上架前必须改掉**（plans.md P1）。

已完成（2026-11-21，手测通过）：工具栏图标只跟「Turn on this extension」走：打开就是彩色，关闭就是灰色（`public/icon/gray-*.png`，`npm run icons` 生成），跟当前活动标签页是哪个网站无关。做法是在 manifest 里声明 `action`（不声明的话 Chrome 会在扩展不运行的网站上把图标变灰），后台每次唤醒和设置变化时 `action.setIcon`；点图标打开设置页。

## 3. 设置页

已完成：仿 YouTube 设置页样式；标签为通用、TL;DR、队列、播放器、评论弹幕（§51.9、§52）、通知（§46）、存储、诊断；顶部显示 YouTube / Gemini 登录状态；首次安装自动打开「诊断」并跑一次自检。

已完成（2026-11-21，手测通过）：除首次安装（`#install`，打开「诊断」）和链接里指定了标签（`#<tab>`、`#log=`）外，打开设置页总是显示「通用」，不再记住上次的标签。

已实现（2026-11-21，待手测）：**扩展语言 = YouTube 的界面语言**，设置页没有语言选项。每次打开 YouTube 页面，单独的 content script（`lang.content.ts`）读 `<html lang>`（读不到时读 cookie `PREF` 里的 `hl=`），`zh*`（含繁体）→ 中文，其他 → English，跟存着的不一样就写进 `settings.lang`，各处由 `initLang` 跟着切换。没打开过 YouTube 时按浏览器语言。不留手动覆盖。

## 46. 页面提示（2026-11-21 手测通过）

**想要什么**：各功能共用的页面提示，样子跟官网的提示条一样，仿手机横幅通知。

**模块**：`src/core/notify.ts`，`notify(text, { action?, error? })`，自己写，不用库（Sonner 的移植、Notyf、Toastify 等都没有「只能横向拖、记住位置」）。每个 content script 是单独的包，但共用一个 isolated world，所以实例挂在 `globalThis`，各功能的提示进同一叠。宿主 `<ytpp-notify>`，内容在 closed shadow root 里；宿主的 `data-text` 是最新一条的文字（给 e2e 读），最新一条带 `.newest`。点击、按键等事件在宿主上拦住，不传给页面（全屏时点提示不会让播放器暂停）。只在出事的那个标签页弹；`role="status"`。

**位置**
- 横向默认居中；上下可选底部（默认，离底 24 px）或顶部（顶栏下面 16 px，不挡搜索框）。
- 按住提示任意处（按钮除外）可以横向拖，整叠一起动，上下不动；拖动时暂停计时。位置存成占窗口宽度的比例，存在 `chrome.storage.local` 的 `notify/x`（只在本机），所有标签页共用，顶部和底部也共用；离窗口边至少 16 px。
- 横向跟迷你播放器或最小化横条（§44）重叠时让开：在底部时抬到它们上方，在顶部时降到它们下方，隔 16 px。看它们的中心在窗口上半还是下半，只躲同一半的。显示期间每 250 ms 重新量一次，迷你播放器出现、移动都跟着变。
- 全屏时挂到全屏的那个元素里。

**样子**：颜色跟主题反过来（看 `html[dark]`）：深色主题浅底深字，浅色主题深底白字；圆角 8 px、Roboto 14 px、仿官方阴影；宽度随文字，最宽 560 px。右侧可带一个蓝色文字按钮。出错的左边加红色警告图标。出现时从边缘一侧滑入并淡入，约 200 ms，消失时反过来。

**时长和叠放**：普通 4 秒、带按钮 6 秒、出错 8 秒（出错优先），设置里可改 2–30 秒；鼠标停在任何一条上时整叠暂停计时。同时最多 N 条（1–5，默认 3），新的最靠边缘，旧的往外推、每条小 4 %，超出时最老的先消失。文字跟正在显示的某条完全一样时不叠加，只把那一条重新计时。

**设置页「通知」标签**（播放器和存储之间）：上下（底部 / 顶部）、「重置为居中」、同时最多显示、三种显示时长和「恢复默认」、「预览」。设置存在 `settings.notify`。「预览」切到最近用过的 YouTube 标签页，再让 `notify.content.ts` 弹一条示例（不切的话人在设置页，看不到）。设置页自己的提示仍用页面里的文字。

**用的地方**：队列的提示全部改用它（原来的 `queue/toast.ts` 删掉）；加入失败、删除已看完失败、列表不存在了等算出错。全屏没有手测（不好触发）。

# 第二部分　TL;DR

## 6. 一句话描述

后台调用免费的 Gemini 网页版（逆向内部接口）读视频，生成要点；点缩略图上的图标在 tooltip 里看。

## 7. 目标与非目标

不做：Shorts、直播中、预告和首映；自抓字幕；读不到字幕时的降级总结；官方 API（只留接口）。

## 8. 关键决定一览

已实现：所有带缩略图的位置都生效；3–7 条要点 + 标题一致性判断（可关）；输出语言是视频自己的语言（下面 §11）；用普通对话（临时对话用不了 YouTube 应用），生成完立即删除；接受封号风险，账号编号 N 可设。

## 9. 架构

已实现：content script（扫描缩略图、可见性、图标、tooltip）↔ service worker（`JobQueue`、`SummaryCache`、`GeminiWebProvider` → `GeminiWebClient`、`PendingDeletes`）。协议细节只在 `GeminiWebClient` 里。

### 9.1 Provider 接口

`SummaryProvider` 已定义，见代码。以后加官方 API Provider 只需新增一个实现（plans.md P3）。

## 10. Gemini 网页版协议

已实现，见 `src/features/tldr/client.ts`、`protocol.ts`。要点：

### 10.1 抓取 token
从 `/u/N/app` 页面取 `SNlM0e`（`at`）、`cfb2h`（`bl`）、`FdrFJe`（`f.sid`）、`d2zJAe`（`processSession` 的 API key，跟登录无关）；拿不到 `SNlM0e` 即未登录或第三方 cookie 被屏蔽。

### 10.2 发起生成
两条通道，发的都是 `buildInner()` 那个数组，用账号默认模型：
- **`processSession`（优先）**：网页前端从 2026-10 起改用的新协议，细节见 §10.8。
- **`StreamGenerate`（后备）**：旧接口，不发模型 header。

一条通道报 `protocol` 或 `auth` 时换另一条；`quota`、`blocked`、`transient` 不换（额度和封锁按账号算）。哪条成功，之后先用哪条（只记在内存里）。两条都失败时优先报 `auth`。新通道 20 秒内没有回答帧、或 180 秒没结束，算 `protocol`。切换写 warn 日志；自检「实际总结」一项显示走的是哪条。

### 10.3 解析返回
两条通道的回答数组形状相同，取正文共用一段代码（`readAnswer`）；正文在中间某帧，取最后一帧有正文的。`StreamGenerate` 按长度前缀切帧（UTF-16 长度，含换行）；`processSession` 见 §10.8。

### 10.4 删除对话
`batchexecute`，RPC `GzXR5e`；失败的进 `PendingDeletes` 重试。

### 10.5 鉴权
`credentials:'include'` 带浏览器 cookie；**不轮换 cookie**；Origin/Referer 用 declarativeNetRequest 改成 gemini.google.com（覆盖 `gemini.google.com` 和 `geminiweb-pa.clients6.google.com`）。`processSession` 另要 `SAPISIDHASH`，靠 `cookies` 权限读 `SAPISID`。

### 10.6 YouTube 应用的前提条件
需要开启 Gemini 应用活动记录、在 gemini.google.com/apps 启用 YouTube 应用；没字幕的视频读不了。

### 10.7 现状（2026-11-21）

- 默认走 `processSession`，`StreamGenerate` 当后备（§10.2）。2026-11-21 手测：自检和首页批量都走新通道，没有回退。旧接口当天仍能用。
- 协议都关在 `GeminiWebClient`（I/O）和 `protocol.ts`（纯函数）里，接口变了自检会报 `protocol`。
- 每次请求前都实时抓一次 `/app` 页面取凭证（plans.md P2 打算缓存）。
- 两条都是内部接口；都失效时的后备是 plans.md P3（官方 API）。

### 10.8 `processSession`

已实现（2026-11-21 手测通过），见 `client.ts` 的 `viaSession`。参考 zexadev/gemini-web2api-go 的 `internal/app/webchannel.go`；它没测过 YouTube 应用，我们实测能用（用当周新上传的视频验证，回答里有只在视频里讲的细节）。单个视频约 6–7 秒，5 个一批约 12–15 秒。

地址 `geminiweb-pa.clients6.google.com/v1/processSession`，Google WebChannel，JSPB 可读版本。

1. **握手** `POST count=0`。认证放在 URL 的 `$httpHeaders`（`"K:V\r\n"` 拼接）：`X-Goog-Api-Key`（`d2zJAe`）、`x-goog-ext-525001261-bin: CAE=`（只有字段 1=1）、`X-WebChannel-Content-Type: application/json+protobuf`（不加返回 400）、`Authorization: SAPISIDHASH <ts>_<sha1("<ts> <SAPISID> https://gemini.google.com")>`、`X-Goog-AuthUser: N`（新地址没有 `/u/N`）。响应头 `X-HTTP-Session-Id` 是 `gsessionid`，响应体 `["c", SID, …]` 是 `SID`。
2. **下行** `GET …&RID=rpc&AID=<最后的 id>&CI=0&TYPE=xmlhttp` 长轮询，断了带 `AID` 重连。帧是「长度\n JSON」，**长度不含换行**，按 UTF-16 计。
3. **上行** 三次 `POST count=1&ofs=<n>&req0___data__=<JSON>`：`ofs=0` 发 inner（prompt 一格清空）；收到确认 `[[]]` 后等 500 ms 用 `ofs=1` 发 prompt（3 秒没确认也照发）；候选 flag=1（生成完毕）后用 `ofs=2` 发收尾，早发拿不到正文。
4. **下行内容** `[null, [seq, null×5, [[flag, [rid], null, [null, null, null, X]]]]]`，`X` 是旧响应的数组。结束帧 `[null, null, null, []]` 或 `["close"]`。
5. **错误** 在 `{"__sm__": {"status": …}}` 里，HTTP 仍是 200；16 → `auth`，其余 → `protocol`。
6. 删对话照旧用 `GzXR5e`。

**坑**：不带 `SAPISIDHASH` 不报错，而是当匿名用户回答，对话不进账号；只带 `X-Goog-AuthUser` 也一样。读不到 `SAPISID` 时报 `auth`（会换到旧通道），但哈希失效这种情况目前检测不到。

## 11. Prompt 与输出格式

已实现：要求严格输出 JSON；读不到内容时输出 `{"status":"no_transcript"}`，禁止编造；解析失败时把原文当 markdown 显示并缓存。

已实现（2026-11-21，待手测）：**TL;DR 用视频自己的语言**，跟扩展语言无关：视频主要说什么语言，要点和标题判断就用什么语言（越南语视频就是越南语）；中文按视频自己用的简体或繁体，分不清时用简体。由 Gemini 判断（它读了字幕），`lang` 字段填它判断的语言代码，只作参考。批量请求里每个视频各按各的语言。比较过的其他取语言办法见 plans.md P23。

## 12. 预生成、任务队列与限流

已实现：全局唯一队列、串行、一次请求最多合并 5 个视频；优先级 点击 > 可见 > 其余；请求间隔 5–10 秒；上限每小时 40 / 每天 200（手动点击不受暂停影响但计数）；只在有 YouTube 标签页在前台时预生成；熔断：1037 暂停到手动恢复，1060 / 1152 / 验证码 / 429 暂停 30 分钟；未登录时全部停。参数都可在设置里改。

## 13. 缓存

已实现：按 videoId 存 `chrome.storage.local`（key `tldr/cache/orig:<videoId>`，不含扩展语言，因为内容是视频的语言；旧格式的 key 在整理时删掉）；成功结果永久（默认 5 MB，LRU）；`unreadable` 缓存 24 小时；错误不缓存。

## 45. 不受 Gemini 个性化设置影响（2026-11-21 手测通过）

**问题**：账号里的个性化设置（给 Gemini 的指令、保存的信息、过往对话）也作用到扩展发的请求上。实例：指令里设了人设（小狗「撒撒」、大量 emoji、称呼名字），Gemini 用人设口吻写了一篇 markdown，没有 JSON，整批失败（2026-11-20 日志）。扩展要公开发布，别人设了什么无从知道，所以做法对所有个性化通用，不针对某一种。

**做法**：两个 prompt（单个、批量）开头三行：这是浏览器扩展发的自动请求，回答由程序解析，没人看；指令、保存的信息、人设、称呼、过往对话一概不适用；不打招呼、不扮角色、不用 emoji 和 markdown。结尾再说一遍「整个回答就是那个 JSON」。临时对话会不会关掉个性化没去查：临时对话用不了 YouTube 应用（§10.6）。

**测试**：网页 UI 开着人设指令跑了 7 批（旧 prompt 4、新 prompt 3），人设都没出现，网页 UI 复现不了；装上扩展后手测通过。以后再出现，兜底（回答不是 JSON 时拆成单个重试）跟 plans.md P16 一起做。

## 20. 一句话描述

设置里二选一：用 YouTube 自带的队列（扩展不管），或者用一个播放列表当队列（接管「加入队列」，顶栏一键播放，看完自动删）。「清空全部」「移除已看完」两种模式都能用。

## 21. 背景（实测结论）

### 21.1 官方队列（TLPQ）
服务器上的临时列表（`TLPQ…`），ID 只存在当前标签页的 sessionStorage，新标签页、其他设备看不到。

### 21.2 「加入队列」是怎么触发的
所有入口都从被点元素冒泡一个 `yt-action`（`yt-add-to-playlist-command`，`listType: PLAYLIST_EDIT_LIST_TYPE_QUEUE`）；在 `document` capture 阶段 `stopImmediatePropagation()` 能完全拦下。例外：标签页已有官方队列且迷你播放器开着时，点缩略图会直接写 TLPQ，不经过这个事件。

### 21.3 改菜单文字
按图标 `ADD_TO_QUEUE_TAIL` 或命令识别，不看文字。新版菜单（`yt-list-item-view-model`）直接改 `textContent`，菜单 DOM 跨页面复用，每次打开都要改、关掉模式要改回；旧版菜单（`ytd-menu-service-item-renderer`）必须设 `ytFormattedString.text`，不能改 `textContent`。

### 21.4 播放列表的读写和播放
- 列出可编辑列表：`playlist/get_add_to_playlist`；读：`browse`（`VL<ID>`，约 100 条一页）；写：`browse/edit_playlist`（每批 100 个操作）；新建：`playlist/create`（ID 可能只有 13 位，不按长度校验）。
- **`DEDUPE_OPTION_SKIP` 不起作用**；写后几秒内读到的可能是旧数据。新建的列表最初 1–2 秒里读起来是「不存在」，`get_add_to_playlist` 里也还没有它，所以读到「不存在」要隔 1.5、3 秒复查，三次都不存在才算被删（2026-11-21 实测）。
- `browse` 返回里列表的条目只看 `playlistVideoListRenderer` 那一块，下面的「推荐视频」也是 `playlistVideoRenderer`，不能算进去。标题在 `metadata.playlistMetadataRenderer.title`（2026-11 起没有 `playlistHeaderRenderer` 了）；空列表没有 `isEditable`，能不能编辑以 `get_add_to_playlist` 为准。
- 「正在播哪个列表」：官方队列在迷你播放器里播放时 `getPlaylistId()` 是空的，要看 `yt-playlist-manager.getPlaylistData().playlistId`（`TLPQ…`）。
- 把列表挂到正在播的视频上：请求 `next` 后依次调 `yt-playlist-manager` 的 `setAutoplayRenderer`、`setPlaylistData`、`setPlayerPlaybackControlData`（只调第二个不够）；本地把当前视频插到最前、自动播放改指第一条。退路是导航到 `watch?v=…&list=…`。
- 正在播的列表被删条目后，官方自动播放会出错，所以由扩展自己切下一条。

### 21.5 认证和身份
在页面里调 `/youtubei/v1/*`，`SAPISIDHASH` + `SAPISID3PHASH`；品牌频道必须带 `X-Goog-PageId`（不带会悄悄按主频道执行）。身份用 `ytcfg` 的 `DATASYNC_ID`。

## 22. 关键决定一览

已实现。要点：自带队列模式扩展完全不管；播放列表模式接管所有走 `yt-action` 的入口；加入时如在看不属于列表的视频，就把列表挂到当前播放上；「播放完后删除」默认勾选，由扩展切下一条再删；设置按身份（频道）分开存；没选列表或无权编辑时不接管；切换模式不迁移数据，已开的标签页提示刷新。

## 23. 架构

已实现：MAIN world（`InnerTubeClient`、`QueueTakeover`、`Identity`、`PlayerWatch`）↔ 固定 tag 的 `postMessage` ↔ isolated（`QueueMode`、`PlayButton`、`WatchedRemover`、`PlaylistTools`）。写操作都在 MAIN world；设置页通过最近使用的 YouTube 标签页读写；纯逻辑不碰 DOM、依赖注入，便于单测。

## 24. 播放列表模式

### 24.1 什么时候接管
同时满足：队列功能开、当前身份选了播放列表模式、YouTube 已登录、选了列表、列表可编辑。没选列表时提示去设置；不可编辑时提示但不清空选择。

### 24.2 加入
已实现：拦下事件 → 先读列表去重 → `ACTION_ADD_VIDEO` → 提示「已加入 · 查看」/「已在 <列表名> 中」；需要时把列表挂到当前播放（§21.4）。失败只提示和写日志，不重试。

### 24.3 改文字
已实现：菜单打开时改成「加入 <列表名>」，不接管时改回。缩略图上的悬停按钮：新版（`toggle-button-view-model`，图标 `ADD_TO_QUEUE_TAIL`）改内层按钮的 `aria-label` 并加 `title`；旧版换 `data.untoggledTooltip`。

### 24.4 播放和看完删除
已实现：顶栏「▶ <列表名> · N」按钮；只在播这个列表时算看完（`ended`，或剩不到 10 秒时切走 / 关标签页）；勾选删除时扩展跳到下一条再删刚看完的；不勾选时交给官方自动播放。最后一条看完后（删掉后列表空了）不再管，接下来放什么照 YouTube 自己的自动播放设置走（开着时结束画面后会放推荐视频，2026-11-21 定）。
- **点顶栏按钮**：正在放这个列表、当前视频在列表里时接着放这一条，不从第 1 条开始：在迷你播放器里就带上当前秒数（`startTimeSeconds`）打开观看页；已经在它的观看页上就什么都不做。其他情况从第 1 条放（2026-11-21 手测通过）。
- **迷你播放器里放完**：用播放器自己的列表切下一条（`getPlaylist()` 找位置，`playVideoAt(i)`），留在迷你播放器里；3 秒内没切过去才退回导航（导航会展开成观看页）。播放器列表里还没有的条目（刚加的）也走导航（2026-11-21 手测通过）。
- **删掉后刷新面板**：正在放这个列表、当前视频却已不在列表里（刚看完删掉了），面板照服务器的列表显示，不改自动播放；不再当成「列表外的视频接上列表」（§24.2）把它放回第一位（`panelView` 的 `attach` 参数，2026-11-21 手测通过）。

### 24.5 选列表、新建、列表被删
已实现：下拉框列出可编辑列表 + 「新建…」（默认名 `YouTube +`，私密；2026-11-21 从 `YouTube+` 改成带空格）；存列表 ID；列表不存在时（复查后确认，§21.4）清空该身份的选择，并提示去设置。不论是检查、加入还是切回标签页时读到的，都这样处理。复查要几秒，期间用户可能已经换了列表：只有选中的仍是复查的那个列表时才清空、才提示（2026-11-20）。

### 24.6 切换模式
已实现：不迁移数据。已开的标签页立刻按新模式走（拦截、菜单文字、顶栏按钮、看完删除），并提示「刷新页面后完全生效」：这个标签页里已有的官方队列保持原样。切回自带队列时，正在播的列表扩展不再管；这时原生的「加入队列」会把视频直接加进这个列表，是原生行为，不拦（2026-11-20 定）。

### 24.7 身份
已实现：按 `DATASYNC_ID` 的 SHA-256 前 16 位区分；`chrome.storage.sync` 存 `queue/profile/<哈希>`（模式、列表 ID 和名字、看完删除）。原来 `chrome.storage.local` 的 `queue/snapshot/<哈希>`（清空快照）不再用，升级时删掉（§47）。

### 24.8 界面跟列表保持同步
已实现：MAIN world 包一层 `window.fetch` 只读监听页面的 `edit_playlist`，扩展自己的写操作直接发同样的事件；300 ms 合并后重读列表、更新数字和面板；读不到预期结果时 1.5 / 3 / 5 秒重读；数字 = 最新列表数据 + 30 秒内已知修改；切回标签页时（距上次 >5 秒）重读。加入和删除一样，几秒内都可能读不到（刚建的列表约 3 秒）。

「30 秒内已知修改」只属于当前选中的列表：换列表、离开接管时清掉；不接管时这个标签页里对选中列表的修改也照记，切回来时叠上去。离开接管或换列表时，为「剩 10 秒关标签页」预签的删除也一并撤掉。

**页面的请求体可能是 gzip**（2026-11-21 实测：面板拖动排序发的是带 `Content-Encoding: gzip` 的 `Request`）：监听按字节判断，需要时解压再读（`innertube.bodyOf`）。只调顺序的请求不上报。

**删除后面板当场跟上**（2026-11-21）：照官方面板「从播放列表中移除」的做法，扩展的删除一成功（看完删除、§47 清空、§48 拖出），就对 `ytd-app` 发 `yt-action` `yt-playlist-remove-videos-action`（`{playlistRemoveVideosAction: {setVideoIds}}`），页面当场把这几行从 playlist manager 的数据里拿掉，不影响播放，不等读取（`dropFromPanel`，只在面板显示的就是这个列表时）。列表删空时 `next` 的回应里整个不带列表（实测），重读也拿不到数据：这时把面板里剩下的行也这样去掉，面板显示「End of playlist」「1 / 0」，跟官方删空一样（`nextHasList`）。

## 25. 清空全部与移除已看完

2026-11-21 改版，见 §47。原来是列表页头部自己加的「⋯」按钮，确认后删、可撤销、存快照、设置页可恢复，这些都删了。

## 47. 清空全部与移除已看完：放进官方 ⋮ 菜单（2026-11-21 手测通过）

**入口**：两项加在官方右上角 ⋮ 菜单的最下面，样子跟官方菜单项一样。「清空全部 / Clear all」用垃圾桶图标（`DELETE`），「移除已看完 / Remove watched」用圆圈打勾图标（`CHECK_CIRCLE_THICK`），文字跟扩展语言走。三个地方有：
- **列表页**（`/playlist?list=…`，头部「全部播放」那一排的 ⋮）：当前身份能编辑的列表都有，两种队列模式下都有。
- **观看页右侧的列表面板**、**迷你播放器下面的列表面板**（两处是同一个 `ytd-playlist-panel-renderer`，用头部右上角的 ⋮）：只在接管时（§24.1）、面板显示的是设置里选的那个列表时才有。
找不到官方 ⋮ 就没有入口，不自己补按钮。

**行为**：点了直接删（每批 100 个），不确认、没有撤销、不存快照。删完用页面提示（§46）说「已删除 N 个」，没有可删的说「没有可删除的视频」；失败照 §26 提示并写日志、不重试，只删掉一部分时说「删除了 N 个，M 个失败」。「已看完」= 观看进度 ≥ 90 %（`isWatchedElsewhere`）。在面板里删完不刷新页面，面板照 §24.8 当场去掉这几行。列表页上删掉的行按视频链接从页面上去掉（isolated world 读不到行的 `data`）。

**正在播的视频被删**（这里的两项，或 §48 拖出）：照常播下去，不受影响。删的时候记下列表里它和它前面的条目（`removedPlaying`）；它播完后，接着播第一条不在其中的（原来排在它后面还留着的，或之后新加的，`nextAfterRemoved`）；没有就交给 YouTube 的自动播放。「播放完后删除」开着关着都这样（`controller.noteRemoved`）。

**实测和做法（2026-11-21）**
- **面板的 ⋮** 是旧版 `ytd-menu-renderer`，弹出的是各处共用的 `ytd-menu-popup-renderer`。下拉框（`tp-yt-iron-dropdown`）的 `positionTarget` 指向打开它的那个 ⋮；它的 `opened-changed` 在定尺寸之前触发（不冒泡，在 document 的 capture 阶段听），这时往弹出菜单的 `data.items` 末尾加两项 `menuServiceItemRenderer`，菜单高度自然算对。下次别的 ⋮ 打开时会重新设 `data`，我们的项不会留在别的菜单里。选中一项时发 `yt-action` `yt-menu-service-item-selected-action`（参数是那一项的数据，会连发两次），在 capture 阶段认出我们的标记就拦下，自己关菜单。
- **列表页的 ⋮** 是新版 `button-view-model`，菜单项在按钮自己的数据里（`onTap.innertubeCommand.showSheetCommand…listViewModel.listItems`），点开时才读。所以在 pointerdown / click 的 capture 阶段往这个数组里加两项 `listItemViewModel`（不该有时拿掉）。新版菜单选中一项时，命令在页面内部执行，没有事件可拦：拦 click，用 §21.3 的 `sheetItems` 按下标认出是我们的项。
- 我们的项的命令里带标记 `ytppQueueTool: { op, listId }`（`toolOf`）。代码：`queue/page-menus.ts`（MAIN world：加项、认点击），`queue/playlist-tools.ts`（isolated：列表页的列表能不能编辑、执行删除、提示）。

**删掉的**：自己的「⋯」按钮和确认框、撤销、快照（`queue/snapshot/<身份>`，升级时清掉）、设置页「最近一次清空 · 恢复」、存储页的「队列快照」一类。

## 48. 拖出列表面板删除（2026-11-21 手测通过）

**想要什么**：在观看页右侧、迷你播放器下面的列表面板里，把一条视频拖到面板外面松开，就从列表里删掉。只在接管时、面板显示的是设置里选的那个列表时有；列表页没有。（原来想做的「列表页多选后删除」不做了。）

**行为**
- 拖到面板外面时，跟着指针的那一行盖一层红色，写「松开即删除 / Release to remove」；拖回面板里提示消失，变回普通排序。在面板里面松开照官方原样排序。
- 松开后那一行马上消失，不弹提示，没有撤销。失败时那一行回到原位，弹「删除失败」并写日志，不重试。
- 拖出去的是正在播的视频：跟 §47 一样，照常播完，再接着播原来排在它后面的那条；没有就交给 YouTube 的自动播放。

**实测（2026-11-21）**：面板的拖动不是 HTML5 drag，是 Closure 的 DragListGroup（鼠标事件）。拖动时把行复制一份（class `dragging`）挂到 `ytd-app` 下跟着指针走，指针离开列表时原来那行藏起来。在列表外松开时，页面先把行放回原位，然后**仍然照常算 drop**：按原位算出前一条，发一个 `ACTION_MOVE_VIDEO_AFTER`（移回原处）。请求体是 gzip 压缩的 `Request`，发完页面再自己刷新面板。改成删除后，回应里带着官方的「已从…中移除 · 撤销」提示（`actions` 里的 `openPopupAction`）。

**做法**（`queue/page-menus.ts`）
- pointerdown 时记下是哪个面板的哪一行，以及当时面板里的列表。pointermove 时看 `ytd-app > ytd-playlist-panel-video-renderer.dragging` 在不在、指针在不在面板外，给副本加上提示。
- pointerup 时如果在面板外，就「挂号」5 秒：页面随后发的那个移动请求（`moveToRemove` 认出是这一条），在 fetch 包装里换成 `ACTION_REMOVE_VIDEO` 发出去，页面不会再发移动；回应交给页面前去掉 `actions`，所以不会弹官方提示。成功后照 §24.8 从面板数据里拿掉这一条，并上报修改；失败时把那一行露出来，通知 isolated 弹提示。
- 松开后那一条（按 setVideoId）藏 30 秒：面板上哪个行元素显示它就藏哪个。行元素会被复用给别的条目；页面在请求后自己刷新面板时，读取晚几秒的话会把它带回来。

## 32. 一句话描述

### 40.2 单个视频循环（2026-11-21 手测通过）

**想要什么**：播放器里一个看得见的循环按钮，一个按钮来回切换开 / 关（官方只在右键菜单里有「循环播放」）。

**设置**：「设置 → 播放器 → 子功能」第五项「循环播放按钮」，默认关。没打开（或播放器功能、「启用 YouTube+」关着）时播放器里完全没有这个按钮。循环正开着时去设置里关掉：按钮消失，循环也一起停。

**出现在哪**（都只有一个按钮）：
- 观看页普通、影院、全屏：底部左侧控件栏，紧贴在 ▶ 右边（▶ 和 ⏮⏭ / 🔊 之间）。
- 迷你播放器，「迷你播放器控件」开着：悬停后的底部控件栏里，同上（▶ 和 🔊 之间）。
- 迷你播放器，「迷你播放器控件」关着：画面正中大 ▶ 的右边，跟大 ▶ 一样大；▶ 本身位置不动。
- 不做：频道页预告片、Shorts（本来就循环）、悬停预览、站外嵌入播放器。

**样子**：圆环箭头里一个 ▶（24×24，线宽 2，圆角线头，跟官方新版图标一样）。控件栏里跟 🔊 一样是 30% 黑的圆底，40 px（全屏的大控件模式 48 px，图标不放大），上下跟官方按钮对齐。开：图标纯白；关：图标 50% 透明；没有红线。悬停提示用官方提示的样式：关着时「循环播放」，开着时「关闭循环播放」，跟随扩展语言（即 YouTube 的语言）。不加快捷键。

**行为**：只对当前视频有效，换视频 YouTube 自己就关（实测）。按钮和右键菜单「循环播放」是同一个状态，两边同步。播放列表里、开着自动播放时也一直重播当前视频，不跳下一条。

**跟队列（§24.4）**，只在接管并播放选中的列表时：
- 循环开着时这个视频不算看完：不预签删除（已预签的，关标签页时也不发），「剩不到 10 秒时切走 / 关标签页」不算。
- 视频自动从结尾跳回开头算循环一次；自己把进度条拖回开头不算。
- 循环过至少一次后，在列表里切到另一个视频（列表面板里点别的、⏭ 下一个）：把刚才循环的视频当看完删掉。去看列表外的视频、关标签页：不删。
- 没勾选「看完删除」时都不删。

**实测（2026-11-21）**：右键菜单的「循环播放」改的就是 `<video>` 的 `loop` 属性；播放器接口 `setLoopVideo(b)` 改同一个属性，菜单勾选也跟着变；直接写 `video.loop` 菜单勾选不变，所以按钮要经 MAIN world 调 `setLoopVideo`。`loop` 属性的变化在 isolated world 里用 MutationObserver 看得到。站内跳到别的视频后 `loop` 回到 false。官方按钮不会给我们的按钮显示提示，提示要自己建（`div.ytp-tooltip.ytp-bottom` 放在 `#movie_player` 下，套官方样式，按钮上方 22 px）。迷你播放器正中那排是 `.ytp-miniplayer-controls` 里三个容器（上一个 / ▶ / 下一个，两边是空的），按钮挂在 ▶ 容器右侧、绝对定位。新视频刚开始时 `getPlaylistId()` 会空一会儿：循环过的视频离开时，等读到新视频的列表（或用网址里的 `list=`）再判断，最多等 5 秒。

## 44. 迷你播放器最小化（2026-11-21 手测通过）

**想要什么**：迷你播放器能缩到一边，不挡页面内容，视频接着播，需要时再点回来。

**设置**：「设置 → 播放器 → 子功能」第六项「迷你播放器最小化按钮（✕ 左边）」，默认开。关掉时按钮和横条都消失，迷你播放器照常显示；记住的最小化状态保留。

**按钮**：迷你播放器右上角，紧贴在关闭（✕）左边。跟 ✕ 一样 40×40，白色「—」，悬停时跟官方按钮一起出现。悬停提示「最小化」在按钮正下方（跟左上角「展开」的提示一样），跟随扩展语言（即 YouTube 的语言）。

**最小化后**：页面左下角一条横条（离边 16 px），只显示视频标题，太长时省略号；样子跟迷你播放器下面的标题栏一样，跟随 YouTube 的浅色 / 深色主题。不管迷你播放器原来在哪个角都放在左下角。视频继续播；列表里换到下一条时横条上的标题跟着变。

**还原**：点横条任意位置（或用键盘 Enter / 空格），迷你播放器回到原来的位置和大小，下面的列表面板一起回来。

**记住**：最小化状态存在 `chrome.storage.local` 的 `player/miniMinimized`，刷新页面、下次打开迷你播放器时还是横条；所有标签页同步。回到观看页（没有迷你播放器）时横条不显示，状态不变。

**做法**：不关迷你播放器，只用 CSS 把整个 `ytd-miniplayer` 藏起来（`opacity: 0` + `clip-path: inset(50%)` + `pointer-events: none`），所以列表面板跟着藏，YouTube、拖动和记位置（§35.2、§35.3）、队列都感觉不到变化。横条是 `html` 下的一个元素，内容在 shadow root 里，不受 YouTube 样式影响，主题变量照样传进去。悬停提示跟循环按钮（§40.2）共用 `tooltip.ts`。

**实测（2026-11-21）**：✕ 是 `.ytp-miniplayer-scrim` 里 40×40 的绝对定位按钮（右上角，padding 8 px，z-index 67），自己没有悬停提示。另有一个 0×0 的 ✕ 在 `.ytp-miniplayer-buttons` 里，不用它。标题在 `ytd-miniplayer-info-bar` 的 `h1.ytdMiniplayerInfoBarTitle`。藏起来以后视频一直在播，原来那块地方点下去落到后面的页面上。

## 49. 观看页往下滚时播放器缩成小窗（2026-11-21 手测通过）

**想要什么**：观看页往下滚去看评论时，播放器缩成一个小窗，腾出地方看评论；视频接着播，回到上面恢复原样。替换掉原来的置顶和影院模式自动切换（§36.1、§36.2）。

**设置**：「设置 → 播放器 → 子功能」第三项「观看页往下滚时播放器缩成小窗（右下角，可拖动）」，默认开；设置键沿用置顶时的 `stickyPlayer`。「重置迷你播放器和小窗的位置」两个位置一起清。

**什么时候变小**：播放器在页面里的那块地方，在顶栏下面露出的不到一半时变成小窗，露出超过一半时回去，中间留 ±24 px 的回差。普通模式、影院模式都一样，影院模式不再自动切到普通模式。全屏时不变。

**样子**：跟官方迷你播放器默认一样大（400×225），圆角 12 px、阴影。默认在右下角，「回到顶部」左边 16 px，底边对齐（离窗口右边 88 px、下边 24 px）。悬停时显示播放器自己的控件栏（YouTube 按小尺寸自己排）。左上角「展开」按钮（两个朝外的箭头，40×40，跟控件栏一起淡出），悬停提示「展开」在按钮正下方；点了回到页面顶端，小窗回去。

**拖动**：从画面上按住拖（控件栏、按钮、片尾推荐、广告上不触发）；松手离边 <24 px 吸边，跟迷你播放器（§35.2）一样。位置存 `chrome.storage.local` 的 `player/floatPos`，跟迷你播放器的 `player/miniPos` 分开；拖完不暂停。

**小窗时**：按 `t` 或点影院模式按钮，直接回到页面里、回到顶端（§36.3）；点当前视频的时间戳只跳时间，不滚动页面（§36.4）。

**层级**：盖住页面内容，在顶栏（2020）、「回到顶部」（2025）、左侧导航抽屉和迷你播放器（2030）下面。

**做法**：`float.ts`，判断和默认位置在 `float-state.ts`。小窗就是给 `ytd-watch-flexy #player-container` 加 `position: fixed`，位置用 CSS 变量；原来的地方由它的父元素占着，页面不跳。变小、变回后各发一次 `resize`（一帧后、400 ms 后），YouTube 就按新盒子重排视频和控件栏；小窗时视频又被 YouTube 撑大（换视频、广告）也补发。切影院模式时直接变回去，之后 300 ms、1 s 再各判断一次。离开观看页（`yt-navigate-start`）先变回去，免得播放器搬去迷你播放器后留下空的黑框。小窗时把父元素（`ytd-watch-flexy :has(> #player-container)`）提到 `z-index: 2019`。

**实测（2026-11-21）**：`#player-container` 的祖先都没有 `transform` / `contain` / `filter`，`fixed` 有效。父元素在普通模式是 `#player-container-inner`（用 padding 撑高），影院模式是 `#player-full-bleed-container`（自己有高度），子元素 fixed 后高度都不变。YouTube 不会自己发现盒子变了，发一个 `resize` 就重排（不用 `setInternalSize`）。切影院模式后 YouTube 要过一会儿才把 `#player-container` 搬到新位置，那一刻判断会读到旧布局。影院模式下父元素自成一层，盒子自己的 z-index 再大也只在层里算，右栏缩略图会盖住小窗，所以提父元素；它背景透明，不挡东西。

**没测到的**：小窗时换视频（右侧推荐、列表下一个）、广告、全屏进出、直播聊天、窗口缩放；L1 `float-state.test.ts`、L4 `player.spec.ts` 观看页部分写了没跑。

## 50. 迷你播放器弹出到桌面（2026-11-22 手测通过）

**想要什么**：迷你播放器放到整个桌面上随便挪，切到别的标签页或程序时也浮在最上面，边干别的边看。只放画面和控件；列表在 plans P25。

**用词**：**浏览页**是 grid（首页、搜索结果、频道页、订阅页……），里面一个个视频叫 **card**；**播放页**是左边播放器、下面评论、右边一列缩略图。

**设置**：「设置 → 播放器 → 子功能」第七项「迷你播放器弹出到桌面」，默认开，一个开关管按钮和快捷键。下面一个录制框：点一下再按组合键；至少带一个 Shift / Ctrl / Alt；按到 YouTube 自己用的（Shift+N / P / , / . / /、Shift+=、Ctrl+← →）提示冲突不保存；「恢复默认（Shift+I）」；「清空」= 只关快捷键。快捷键存在 `settings.shortcuts.pip`（扩展第一个快捷键，`shortcut.ts`），按 `KeyboardEvent.code` 匹配；焦点在输入框里不触发。浏览器没有 `documentPictureInPicture` 时整项变灰，写「需要 Chrome / Edge 116 以上」。「重置位置」顺带清 `player/pipSize`。自检「浏览器支持弹出窗口（Document PiP）」，不支持时是黄色「注意」（不算失败，§5）。

**打开**：迷你播放器左上角「展开」右边一个按钮（40×40，白色线条图标：大窗口右下角开口放一个小窗、箭头指向它，跟「展开」同画法；悬停提示「PiP (Shift+I)」在正下方，两种语言一样，括号跟着设置变），或者快捷键。在播放页按快捷键：先做 `i` 做的事（回到上一个浏览页，播放器缩进迷你播放器），再弹出。迷你播放器最小化成横条（§44）时也能弹出。不在切走标签页时自动弹出。

**弹出期间**：PiP 是一种迷你播放器，主页面一直在迷你播放器状态。主页面的迷你播放器藏起来（同 §44 的办法），左下角横条写「在弹出窗口里播放」，点了收回（§44 的横条让位；两条横条共用 `mini-bar.ts` 的样子，通知 §46 避开显示着的那条）。浏览页点 card、列表自动下一条，新视频在 PiP 里接着播。PiP 里：
- 控件栏始终是播放页那套（⏮⏭、音量、时间、字幕、齿轮），进度条在按钮那一行上沿；最小化按钮（§44）藏掉；自由拖动（§35.2）不起作用，用系统标题栏拖；循环按钮（§40.2）跟过去。
- 右上角一个 ✕（悬停时跟控件一起淡入淡出，提示「关闭 (Shift+I)」），跟标题栏的 ✕ 一样收回。标题栏的「返回标签页」藏掉（`disallowReturnToOpener`），它跟 ✕ 作用一样。
- 按键（YouTube 的快捷键传不进来，自己接，经 MAIN world 调播放器接口）：空格 / `k` 播放暂停，← → 5 秒，`j` `l` 10 秒，↑ ↓ 音量，`m` 静音，弹出快捷键收回，`f` 全屏（见下）。其他键不接。
- 窗口大小和位置交给 Chrome：它会记住用户上次拖到哪、拉多大，前提是每次请求同样的大小。第一次按迷你播放器的宽度（§35.3，16:9）算一个大小存进 `player/pipSize`，以后都请求它。脚本设不了位置。

**收回**：快捷键（主页面或 PiP 里）、横条、✕（播放器里或标题栏）：视频回到迷你播放器原来的地方接着播；弹出前是最小化横条的，回到横条。主页面离开迷你播放器状态时跟着收回：去播放页（`yt-navigate-start` 到 `/watch`）；后退 / 前进回 `/watch` 且网址里的视频就是正在播的（官方会展开；视频不一样时官方不展开，PiP 也留着）；Esc 关掉迷你播放器。整页刷新、关标签页时浏览器自己关 PiP。

**全屏**（PiP 里全屏按钮、`f`、双击画面）：PiP 窗口里不许全屏，在 PiP 里点也不能让标签页全屏。所以收回 → 切回标签页、浏览器窗口全屏（像 F11；background 调 `windows.update`，原来的窗口状态记在 `storage.session`）→ 点迷你播放器的「展开」回到播放页 → 播放器盖满整页。Esc、`f`、全屏按钮、双击画面、F11 退出：窗口恢复原状，回到 PiP（先缩成迷你播放器再弹出）。浏览器不许打开 PiP 时（没有用户操作）退回迷你播放器，弹通知「浏览器不许按 Esc / F11 直接弹出窗口，已回到迷你播放器」，上面的「弹出」按钮再弹出；手测时 Esc 和 F11 都直接回到了 PiP。在这个全屏里按弹出快捷键：先退出全屏再弹出。`pip-full.ts`。

**做法**：Document PiP（`documentPictureInPicture.requestWindow()`），桌面版 Chrome / Edge 116+。把整个 `#movie_player` 搬进 PiP 窗口（原型比较过只搬 `<video>`、控件自己画，没必要）。`pip.ts`：
- 先 `requestWindow`（要趁用户的点击或按键还算数），再搬播放器；样式表整套复制过去（`cssRules` 转成 `<style>`，跨域的用 `<link>`），我们自己的 `ytpp-*` 样式和深色主题跟着变。收回时放回 `ytd-player #container` 原来的位置。
- 大小：PiP 里发 `resize` 不管用，经 MAIN world 调 `setInternalSize(宽, 高)`；YouTube 每换一个视频（广告也算）把视频改回迷你播放器的大小，看着 `<video>` 的 `style` 一变就再调。
- 拖动：进度条、音量的拖动 YouTube 在主页面 `document` 上等 `mousemove` / `mouseup`，把 PiP 文档里的 `mousemove` `mouseup` `pointermove` `pointerup` `pointercancel` 转发过去。
- 控件栏：PiP 里的播放器还带着 `ytp-player-minimized`，PiP 的样式里藏掉 `.ytp-miniplayer-ui`、强制显示 `.ytp-chrome-bottom`，进度条从 `bottom: -1px`（半截在窗口外）挪回 `top: -3px`。
- 找播放器：弹出后 `document.querySelector('#movie_player')` 找不到，在 `document` 上 capture 的媒体事件也收不到。`core/pip-doc.ts` 先找主页面、再找 PiP 文档，并在每个 PiP 文档上也挂监听（`documentPictureInPicture` 的 `enter` 事件，两个 world 都看得到）；队列 `main-world.ts` 的 `player()` 和 `timeupdate` / `ended`（看完删除、自动下一条）、循环按钮、自检都用它。
- 后退 / 前进不发 `yt-navigate-start`，只有 `popstate`：在 `window` 上 capture 接（排在 YouTube 前面），从 MAIN world 读正在播的视频 id 比网址。
- 播放页的「迷你播放器」按钮已经没有了：在 `document` 上发一个合成的 `i` keydown，YouTube 认。

**实测（2026-11-21–22）**：搬到另一个文档播放不停；点 card 14 次、自动下一条、广告前后、后退，YouTube 从来没把播放器搬回去。PiP 文档 `fullscreenEnabled` 为 false，`requestFullscreen()` 报「Fullscreen is not supported」；在 PiP 里点按钮调 `opener` 的 `requestFullscreen()` 报「not granted」。每次请求不同的大小时，Chrome 不恢复上次的位置。YouTube 没用 Shift+I。

**改不了的**：标题栏（网址、✕）是 Chrome 画的，去不掉；只能由用户点击或按键打开；同时只有一个 PiP 窗口；Wayland 下可能不置顶（没测）。

**测试**：L1 `shortcut.test.ts`（没跑，用户那边 `npm test` 有别的失败待查）；L4 `pip.spec.ts` 前两条用户跑过通过，全屏一条没跑。

# 第五部分　评论弹幕

## 51. 评论弹幕（2026-11-22 手测通过）

**一句话**：评论以字幕卡的形式出现在播放器顶部，一次一条。带时间戳的评论在那个时间点出现；其余的用本地算法按热度撒到全片，或者由 Gemini 读字幕后放到相关的时刻。参考 ComVi（CHI 2026，arXiv 2603.26173）：借用它的阅读时长、赞数归一化和「同一时间只显示一条」的排期；不照搬它看画面、用全部评论的做法。

### 51.1 范围和开关

- 只在 `www.youtube.com/watch` 的普通模式（含 §49 小窗）、影院模式、全屏里显示。迷你播放器（含 §44 横条）、弹出窗口（§50）、广告（`#movie_player.ad-showing`）时隐藏。嵌入播放器、youtube-nocookie、music.youtube.com、Shorts 不管；直播和直播回放（`videoDetails.isLiveContent`）不做，按钮变暗、提示写明。
- AI 只走 Gemini，不内置本地模型；不让 AI 看画面，只靠字幕和评论文字。
- 设置页全局开关 `features.danmaku`，默认关；关时没有按钮、不拉评论、不调 Gemini。
- 播放器控件栏里字幕按钮左边一个开关按钮（`button.ts`），像字幕按钮一样记住状态（`settings.danmaku.active`），对所有视频生效；关着时什么都不跑。图标自己画（用户认可）：对话气泡，关 = 空心，开 = 实心，处理中 = 右上角蓝点闪，没有评论 / 直播 = 变暗。提示第一行是开关状态，下面是评论条数、卡片数、定位方式、退回原因；开调试时加各环节耗时。不加快捷键。
- 只在打开观看页、按钮开着时处理当前视频；不给队列、缩略图上的视频提前生成。切到别的视频（含自动播放下一个）：立刻停止拉旧视频的评论，没发出去的 Gemini 批次取消，已发出的跑完、结果照样写进缓存。离开观看页（迷你播放器）时会话继续。

### 51.2 拉评论

- MAIN world（`danmaku-main.content.ts`、`main-world.ts`）直接调 InnerTube `next`，不滚动页面、不碰评论区 DOM；在页面里解析完，只把结果传给 isolated 一侧（`bridge.ts`、`rpc.ts`）。固定 `context.client.hl = 'en'`：数字格式跟着 `hl` 变（en「9.3K」、zh-CN「29万」、de 给精确数），固定以后只需解析 K / M / B，发布时间也是英文。没登录时不签名照样调（`innertube.ts` 的 `prepare(…, { anonymous: true })`），拿到的数据一样。
- 视频信息取 `#movie_player.getPlayerResponse().videoDetails`（id、标题、时长、`isLiveContent`）；等它报的 id 跟网址一致再开始。
- 第一次用 videoId 调：评论区是 `contents.twoColumnWatchNextResults.results.results.contents[]` 里 `sectionIdentifier === 'comment-item-section'` 的 `itemSectionRenderer`，`contents[0].continuationItemRenderer…continuationCommand.token` 是第一页。「最常重播」在 `frameworkUpdates…macroMarkersListEntity.markersList`（`MARKER_TYPE_HEATMAP`，100 段 `{startMillis, durationMillis, intensityScoreNormalized}`），只有播放量够高的视频才有。
- 往后翻：`onResponseReceivedEndpoints[*].*.continuationItems` 最后一项的 `continuationItemRenderer`（`continuationEndpoint` 或 `button.buttonRenderer.command`）。第一页的 `commentsHeaderRenderer.countText` 是精确总数。评论在 `frameworkUpdates.entityBatchUpdate.mutations[].payload.commentEntityPayload`，每页 20 条，顺序按线程列表。只用一级评论（`replyLevel 0`），回复数算进热度。
- 默认「热门」排序，不全拿：拉到 `firstBatch`（100）条先排一次，后台继续拉；上限 = max(200, 每分钟 15 条)，封顶 300（实测约 300 条以后混进大量 0–1 赞的新评论）。速度：第一次约 0.8 秒，之后每页 250–500 ms，只能串行，600 条 11.7 秒没被限流。
- 时间戳用 YouTube 解析好的 `content.commandRuns[].onTap.innertubeCommand.watchEndpoint`：`startIndex` / `length` 是 UTF-16 下标；要核对 `videoId` 是当前视频（链到别的视频算链接）；`0:00` 没有 `startTimeSeconds`，缺省 0。会员表情在 `attachmentRuns`，显示成和文字一样高的行内小图。
- 评论一视同仁：不按语言筛选，置顶和作者评论不加权、不加标记。

### 51.3 过滤和热度

- 本地过滤掉（不送 Gemini，也不显示）：带链接的、纯表情的、太短的、重复的（只留赞最多的一条）。「太短」按文字算，中日韩文字一个算 3 个拉丁字母（实测只数字符会滤掉一半中文评论）。
- 热度 = 赞数权重 × 赞数（Box-Cox，λ 用最大似然在 −2…2 上按 0.1 搜）+ 回复权重 × log(回复数) + 新旧权重 × 新旧（「3 weeks ago」换算成天数，读不出的按中位数），三项各自归一化到 0–1。新旧权重是负数就越旧越优先。

### 51.4 带时间戳的评论

- 每个时间戳出现一次，每次显示整条；超出时长的忽略。**真目录**（第一个是 0:00、至少 5 个时间戳、每行只是时间 + 短标题）只在 0:00 显示一次。
- 优先占位；那个时刻被占了只往后推，最多 5 秒，推不进去就放弃，不提前（免得剧透）。
- 同一时刻（从第一条起 ±2 秒内）放进同一张卡，按赞数轮流，最多 3 条，角上标「1/3 +4」；轮播卡最多能推迟它自己的时长。

### 51.5 定位方式

设置里全局选「本地」（默认）或「AI」；切换后当前视频马上按新方式重排。

**本地**（`local.ts`）：每分钟条数 = 1 + log₁₀(总评论数)，夹在 1–6；视频（开头 5 秒除外）切成 30 秒的窗口，名额按 `1 + 重播权重 × 该窗口的「最常重播」热度` 分；按热度从高到低轮流发到各窗口（窗口顺序随机），窗口内均分再随机偏移；随机数用 videoId 当种子，同一个视频每次一样。带「结尾」「反转」「ending」「twist」这类词的只放最后 20%。

**AI**（Gemini 的 YouTube 应用读字幕）：
- 每批约 100 条，一次请求给视频链接和评论，紧凑格式每条一行：`id|秒|置信度`、`id|a`（对不上具体时刻）、`id|x`（广告、引流、骂人、无关，不显示）。提示词在设置页可整段编辑（`{{url}}` `{{title}}` `{{duration}}` `{{comments}}` 占位），默认那份定义了每档置信度的含义、「拿不准就用 a」、时间都在 0 到时长之间，开头是 §45 的说明。
- 只用置信度 ≥ 0.9（可调）的时间；其余的和超出时长的当 ambient。实测：≥ 0.9 的误差都在 5 秒以内，0.5–0.8 的差 2–359 秒。缓存存 Gemini 的原始判断，分界改了对缓存也生效（`withCutoff`）。中文视频的评论多是对画面、配乐、梗的反应，常常一条 ≥ 0.9 的都没有。
- 打分 = 2 × 置信度 + 1 × 热度 × 显示时长，动态规划选；每条 AI 评论只出现一次。ambient 只用来填空：时间轴上空闲超过 20 秒就按热度补一条，放在那段里最常重播的地方。
- 分层上屏：Gemini 回来之前只显示带时间戳的（AI 没看过的评论可能是剧透）；每批回来后重排没播到的部分。
- 请求走 TL;DR 服务的同一个串行队列（`TldrService.ask()`，消息 `YouTube+/dm-ask`）：排在所有 TL;DR 请求前面，像点击一样不受每小时 / 每天上限约束，但受熔断约束，算进计数，对话照样删。后台把 Gemini 的完整回答记进日志。
- 一批失败（出错、解析不出来）：15 秒后重试一次，还失败就拆成两半各试一次，最后没答上的评论算「未知」，不显示。没字幕（`no_transcript`）、没登录、额度用完、风控算整个视频用不了，按设置退回「本地」（默认）或「只显示带时间戳的」，不弹提示，按钮提示写原因。很多中文频道没有字幕轨（老高、小Lin 抽查都没有），只能退回本地。

### 51.6 排期

- 纯本地，0.5 秒精度；同一时间只显示一条，两条之间至少空 0.5 秒，评论少时不硬凑。
- 显示时长：两行以内按字数（拉丁字母 0.068 秒 / 个、中日韩文字 0.2 秒 / 个），1.5–5 秒；超过两行每两行一屏、每屏 5 秒。排期时按参考行宽（50 个拉丁字母宽，中日韩文字算 2）估算行数，显示时按真实行数分屏，在分到的时长里滚完。评论长度不设上限。
- 时间轴重排（拉到更多评论、Gemini 回来、改设置）时只改还没开始的卡片：已经开始的留着，往回拖能重放；新的避开它们，不重复已显示过的评论，播放头之前没被占的地方也补上（`mergeTimeline`）。

### 51.7 显示

- 盖在 `#movie_player` 上的一层（`overlay.ts`），`pointer-events: none`；卡片在 shadow root 里（`card-view.ts`，设置页预览共用）。每帧按视频时间画（`frame.ts`），所以暂停、倍速、往回拖都不用特殊处理。
- 顶部居中（2026-11-22 从底部改到顶部，不做拖动），仿官方字幕：半透明深色胶囊底（§52.1），白字，开头 `@handle`（淡一些），不显示头像和赞数；@提及、#话题照原文、不能点。字号 = 播放器高度 × 3.4% × 字号比例（10–64px），行高 1.35，最宽为播放器宽度的 80%；一屏两行，屏与屏之间往上滚；淡入淡出 250 ms。
- 位置和避让（`overlay.ts` 的 `topOf`）：离顶边 4%（至少 12px）；控件显示时（播放器没有 `ytp-autohide`）在顶部标题栏（`.ytp-chrome-top`、`.ytp-fullscreen-metadata`，只算真显示出来、在播放器上四分之一里的）下方 8px，普通模式下它们高度是 0，只有全屏时有标题；字幕框在上半部分时在它下方 8px（实时量，用户可以拖字幕）。挪动有 200 ms 过渡。来源标签和轮播角标在卡片下方。画面里烧进去的字幕测不到。
- 拖进度条落在一张卡中间、剩下不到 1.5 秒的不显示。

### 51.8 缓存、日志和自检

- 缓存按 videoId 存在 `storage.local` 的 `danmaku/cache/<id>`（评论原样、总数、热度曲线、Gemini 的判断、`no_transcript`），有效期 7 天，单独上限 2 MB，满了按最近使用淘汰；设置页「存储」里单独一行。过期后重新拉评论，Gemini 的结果保留，只把新评论送过去。
- 日志：Gemini 的完整原始回答一律记；每个视频一行：拉了几页几条、用了多久、是否来自缓存、定位方式和退回原因、卡片数、首批 / 全部 AI 耗时和每批耗时。
- 自检「能拉到评论（试拉一页）」：用 jNQXAC9IVRw 拉第一页并解析。不试 Gemini（TL;DR 的自检已经验证过通道）。

### 51.9 设置页

「评论弹幕」标签：定位方式、Gemini 用不了时的行为、调试（卡片角上标来源：时间戳 / AI 置信度 / ambient / 本地 / 目录）、提示词编辑框（缺必需占位符时提示、恢复默认；设置都在 storage.sync 一项里，上限 8 KB，所以提示词等于默认时存成空串，用 `promptOf()` 读）、七组可调参数（显示、评论、带时间戳的评论、热度、本地、AI、缓存；每组可恢复默认，全部在 `params.ts`，`paramsWithDefaults` 按组补默认、类型不对退回默认），以及一个循环播放示例卡片的假播放器预览（小 / 中 / 大，可开控件栏、字幕、来源标签）。开发期间放出的参数哪些留给普通用户，用一段时间再定。

### 51.10 测试

- L1：`tests/unit/features/danmaku/`（解析、时间戳和目录、过滤、热度、显示时长、本地分布、同一时刻、动态规划、Gemini 提示词和回答、时间轴拼接和合并、缓存规则）。
- L4：`tests/e2e/specs/danmaku.spec.ts` 9 条，用户跑过全过。多数预先写好缓存（固定评论），卡片时间确定，AI 模式用缓存里现成的判断，不调 Gemini。

## 52. 弹幕风格（2026-11-22 手测通过）

**一句话**：评论在播放器上有三种显示方式，设置 `danmaku.style`：`card`（字幕卡，§51.7，默认）/ `fly`（飞过）/ `panel`（侧栏）。设置页「评论弹幕」最上面一组单选，切换马上生效。主题（配色、字体）和动画还没做（plans.md P29）。

### 52.1 胶囊底

卡片底色是完整的胶囊（`border-radius: 999px`，半径 = 高度一半），两行也是一整个大弧度（原来半径按一行算，两行显得方）。两行时左右内边距 1.05em、一行 0.75em，字不贴弧线；行数一律按宽内边距量，一行能放下的换窄内边距也放得下（`card-view.ts`）。

### 52.2 飞过

- `fly.ts`（纯逻辑）、`fly-view.ts`（画，设置页预览共用）。条目和时间跟字幕卡完全一样：同一时刻轮播卡里的几条按轮播先后各飞一次；超过 `flyMaxLines`（默认 4）行的不飞，行数按卡片的估算（§51.6）。
- 单行长条，换行变空格；底色、字号跟卡片一样。调试时每条后面带来源标签。
- 速度：每条「头部穿过播放器宽度」用 `flyMinSec`–`flyMaxSec`（默认 6–10 秒）里的随机值，评论 id 做种子，往回拖重放时一样；长的待得更久（总时长 = 穿过时间 × (播放器宽 + 条宽) / 播放器宽）。
- 允许重叠：从顶部起分轨道，占播放器高度的 `flyArea`（默认一半），第一条轨道跟卡片一样避开标题栏和上半部分的字幕（`topOf`）。每条放进第一条「前一条已整条进场、自己更快也追不上轨道里任何一条」的轨道；都占满就放进最早空出来的那条。轨道按估算宽度排，画的时候用真实宽度。
- 位置是视频时间的函数，暂停、倍速、往回拖不用特殊处理。

### 52.3 侧栏

- `feed.ts`（数据）、`panel.ts`（画）。播放器右边一个浮层：宽为播放器的 32%（260–440px），上下留出标题和控件栏。像评论区一样：头像、@handle、多久以前（按扩展语言，标「已编辑」）、正文（会员表情是图片，本视频的时间戳可点、跳过去）、赞数、「N 条回复」。只读，不能点赞或回复。
- 不走弹幕的 Session：不筛选、不定位、不调 Gemini、不缓存；自己按 YouTube 的顺序（热门）一页一页拉，滚到离底部 400px 以内拉下一页，直到拉完。在侧栏和其他风格之间切换时重新开始（feed ↔ session）。
- 回复点开才拉。实测（2026-11-22）页面自己的客户端拿到的回复是嵌套的：一级回复各是一个 thread，它的回复（二级）随着一起来，另带「显示更多回复」的令牌，所以显示成树；普通调用拿到的是扁平的 `commentViewModel`。两种都解析（`parsePage` 的 `level`）；回复令牌在 `commentRepliesRenderer.subThreads`（页面客户端）或 `contents`（普通调用）。
- 点击、右键、滚轮不传给播放器（否则点一下就暂停）；滚到底不带着页面滚（`overscroll-behavior: contain`）。外观放在 shadow root 里的内层盒子上：页面 CSS 会盖过 `:host` 的背景。YouTube 强制 Trusted Types，图标用 `createElementNS` 建。
- 头像（`author.avatarThumbnailUrl`）、发布时间、回复令牌只有侧栏用：Session 存缓存前去掉（`lean()`），弹幕缓存大小不变。
