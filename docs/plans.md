# TL;DR

## P2 凭证缓存

**现状**：`generate()` 和 `deleteConversation()` 各自先 GET 一次 `/u/N/app`，每批 4 个请求，其中 2 次是抓页面。浪费的是 HTTP 请求，不是 Gemini 额度；但增加延迟，流量也更像机器。

**改法**：
- 把 `at` / `bl` / `sid` 按账号 N 缓存几分钟，改 N 时清掉。
- 遇到 400 / 405 时清缓存、重抓、重试一次；还失败就按现有的错误映射处理。
- 自检和「我已登录」检测（design.md §15.1）仍然实时抓，不走缓存。
- 做 P4 时还要多缓存一个 API key `d2zJAe`（同一个页面里，跟登录状态无关，很少变）。

跟 P4 基本独立：缓存只管凭证从哪来、什么时候刷新，不管生成走哪个接口。删对话用的 `batchexecute` 迁移后也照样需要这组凭证。

**进度**
- 2026-11-20：定下改法，决定先不做。

## P3 官方 Gemini API Provider

**想要什么**：`StreamGenerate` 下线时 TL;DR 不至于整个失效。

**做法**：实现 `SummaryProvider`（design.md §9.1）。用户在设置里填 AI Studio 的免费 key，直接把 YouTube URL 交给模型。

**好处**：有文档；没有封号风险；不需要 YouTube 应用和活动记录，也不用删对话。
**代价**：用户要自己填 key，不再是零配置，但仍然免费。

**跟 P4 的关系**：原来打算在 P4 之前做，当唯一的后备。现在 P4 有了参考实现，如果 P4 的原型证明 YouTube 应用在新协议下能用，P4 就能当零配置的后备，这一条可以往后放。P3 仍然有价值：新协议也是内部接口，以后照样可能变。

**进度**
- 2026-11-21：优先级改为看 P4 原型的结果再定。
- 2026-11-20：倾向在 P4 之前做。

## P4 `processSession` 新协议

### 现状（2026-11-21 调研）

- 网页前端从 2026-10 中旬起按账号分批改用 `processSession`，所以 DevTools 里看不到 `StreamGenerate`；但旧接口本身没下线，三个参考项目（design.md §19）到 2026-11-21 都还默认走它。
- **已经有参考实现**：[zexadev/gemini-web2api-go](https://github.com/zexadev/gemini-web2api-go)（MIT），2026-11-02 的 v4.27.0 加入，开关 `web_channel`，默认关，留作旧接口出问题时的备用。代码在 `internal/app/webchannel.go`，约 500 行 Go，注释里写了每一步的实测依据。讨论见它的 issue #43、#60。
- 它实测过文本、看图、生图和匿名访问；**没测过 YouTube 应用**。

### 协议要点

**后端没换，只换了传输层。** 上行发的还是我们 `buildInner()` 构造的 inner 数组；下行帧里装的也还是旧响应的数组结构。把下行内容包成旧格式的 `wrb.fr` 行，`parseStream` 和之后的解析都不用改。

地址：`geminiweb-pa.clients6.google.com/v1/processSession`（Google WebChannel，用 JSPB 可读版本，不用处理二进制 protobuf）。

1. **握手**：`POST count=0`。认证信息放在 URL 的 `$httpHeaders` 参数里（`"K:V\r\n"` 拼接）：
   - `X-Goog-Api-Key`：`/app` 页面里的 `d2zJAe`；
   - `X-WebChannel-Content-Type: application/json+protobuf`，不加返回 400「Root element must be a message」；
   - `Authorization: SAPISIDHASH <ts>_<sha1("<ts> <SAPISID> https://gemini.google.com")>`；
   - `X-Goog-AuthUser: N`：新地址没有 `/u/N` 路径，选账号靠这个头；
   - 模型头 `x-goog-ext-525001261-bin`（我们用账号默认模型，只发字段 1=1）。

   响应头 `X-HTTP-Session-Id` 是 `gsessionid`，响应体里 `["c", SID, …]` 是 `SID`。认证在这一步绑到会话上。**握手请求本身必须带登录 cookie**：带了 `SAPISIDHASH` 却没带 cookie，会报 status 16「缺凭证」。
2. **下行**：`GET ?gsessionid=…&SID=…&VER=8&RID=rpc&AID=<最后收到的 id>&CI=0&TYPE=xmlhttp` 长轮询。帧是「长度\n JSON」首尾相接，长度按 UTF-16 计。服务器大约空闲 60 秒就断开，带 `AID` 重连。GET 不需要凭证。
3. **上行**：三次 `POST count=1&ofs=<n>&req0___data__=<JSON>`，顺序有讲究：
   - `ofs=0`：`[[[1, <模型 hex>, "en", <uuid>], 0, null×5, [null×4, [<inner，prompt 一格清空>, null, null, 1]]]]`；
   - 等下行回确认 `[[]]`，**再等 500 ms**，用 `ofs=1` 发 prompt：`[null, [1, null×7, [<prompt>]]]`。不等的话大约 6 次只成功 1 次；确认 3 秒不来也照发；
   - 看到「生成完毕」标记（候选的 flag 为 1）后，用 `ofs=2` 发收尾 `[null, null, null, [1]]`。发早了只有会话 id 和标题、没有正文。
4. **下行内容**：`[null, [seq, null×5, [[flag, [rid], null, [null, null, null, X]]]]]`，`X` 就是旧响应的数组。结束帧是 `[null, null, null, []]` 或 `["close"]`。
5. **错误**：在下行帧的 `{"__sm__": {"status": …}}` 里，HTTP 状态仍是 200。16 = 缺凭证或凭证无效。

### 搬到扩展里要改什么

| 位置 | 改动 |
|---|---|
| `client.ts` | 新增一条通道：握手、长轮询 GET、三次上行 POST 和时序控制。预计 150–200 行 |
| `protocol.ts` | 新增下行帧分类，包成 `wrb.fr` 后交给 `parseStream`；`extractTokens` 多取 `d2zJAe` |
| `wxt.config.ts` | `host_permissions` 加 `https://geminiweb-pa.clients6.google.com/*`；加 `cookies` 权限，用来读 `SAPISID` |
| `installHeaderRule` | 改 Origin / Referer 的规则要覆盖新地址 |
| 删对话 | 不用改，`batchexecute` / `GzXR5e` 照旧 |

工作量预计 1–2 天，包括单元测试和手测。

### 做法

不是把旧接口换掉，而是在 `GeminiWebClient` 里加第二条通道：默认走 `StreamGenerate`，出现 404 / 405 或 `protocol` 错误时自动换到 `processSession`。旧接口下线时扩展自己接上，用户不用做任何配置。

### 风险和不确定的地方

1. **最关键：YouTube 应用在新协议下能不能用，没人验证过。** 后端是同一套，应该能用，但只是推断。
2. **必须登录**：匿名能用新协议，但匿名用不了 YouTube 应用，所以绕不开 `SAPISIDHASH` 和 `cookies` 权限。
3. **时序**：500 ms 是别人测出来的经验值，不是协议规定；批量请求、慢网络下会不会变，不知道。
4. **Service worker 寿命**：长轮询期间 fetch 一直开着。批量请求约 15 秒，离 Chrome 的 5 分钟上限还远，要实测确认。
5. 它也是内部接口，以后照样可能变（所以 P3 仍有价值）。

### 下一步

花半天做原型，**只回答一个问题：YouTube 应用在新协议下能不能用。** 要用真实账号发几次请求，会在 Gemini 活动记录里留几条对话，之后删掉。能用就补成自动回退，P3 往后放；不能用就保持 P3 原来的优先级。

**进度**
- 2026-11-21：调研：找到 zexadev 的参考实现，整理了协议和改动清单（见上）。
- 2026-11-20：决定旧接口还能用就先不迁；当时没找到参考实现。

## P11 迷你播放器面板偶尔缺刚加的视频

原 `queue-test-findings.md` 的 F12。

- **场景**：播放列表模式，迷你播放器在放单个视频，点「加入 <列表名>」。
- **预期**：迷你播放器下面出现列表：当前视频 + 列表原有条目 + 刚加的视频（「1 / 4」）。
- **实际**：完整跑一遍 L4 时出现过一次，面板只有「1 / 3」，缺刚加的那个；顶栏数字是对的。单独连跑 6 次都正常。
- **推测原因**：`syncList()` 用 `next` 读列表，读不到新视频时在 1.5、3、5 秒后再读，最后一次不管满不满足都用（design.md §24.8）。如果 `next` 落后超过约 9.5 秒，面板就缺这一条，之后也不会再补。
- **测试**：`queue-panel.spec.ts` › playlist mode, a single video in the miniplayer…；`modes.spec.ts` › ② single video in the miniplayer…（按正确结果断言，偶尔会失败）。
- **如果经常出现**：最后一次读取仍不满足时，过一会儿再补一次 `syncList`；或者等面板派发的 `yt-playlist-data-updated` 再核对一次。

**进度**
- 2026-11-21：L4 里出现一次，先观察。

# 播放器

## P12 迷你播放器弹出到桌面

**想要什么**：迷你播放器能放到整个桌面上随便挪，切到别的标签页或程序时也一直浮在最上面。

**只能用浏览器的画中画（PiP）**，页面里的元素出不了浏览器窗口。可选做法：

| | 做法 | 能放什么 | 问题 |
|---|---|---|---|
| 0 | 视频画中画：`video.requestPictureInPicture()` | 只有画面和浏览器给的简单控件 | YouTube 已经有了，没有新东西 |
| A | Document PiP（`documentPictureInPicture.requestWindow()`），把整个 `#movie_player` 搬进去 | 官方完整控件，design.md §35.1 的改造也跟过去 | YouTube 切换观看页 / 迷你播放器时会把 `#movie_player` 搬回去，跟我们抢；播放器不知道 PiP 窗口的大小 |
| B | Document PiP，只搬 `<video>`，控件自己画 | 画面 + 自己的控件，以后还能放列表面板 | 多写一套控件，但不太跟 YouTube 抢 |

Document PiP 只有桌面版 Chrome/Edge 116+ 支持。把正在播的 `<video>` 搬到另一个文档，播放不会停。

**列表也能放进去**（只限 Document PiP，视频画中画放不了）。PiP 窗口是一个完整的空白网页，什么 DOM 都能放：
- 不搬 YouTube 的列表面板（`ytd-playlist-panel-renderer`）。它的点击、换视频、删除、拖动排序都靠事件冒泡到主页面的 `ytd-app`，搬过去以后事件只冒泡到 PiP 窗口自己的文档，传不过去；样式要整套复制；YouTube 重绘时还会跟我们抢元素。
- 在 PiP 窗口里自己画列表。数据用队列现有的那套（`rpc.ts` 现在就在刷新侧栏和迷你播放器下面的列表），点某一条时交给主页面去换视频。播放器用方案 A 还是 B 都可以这样做。
- 窗口大小由用户拖，脚本只能定初始大小，列表要能跟着窗口高度变，窗口矮时可以收起。

**改不了的限制**：只能由用户点击打开；窗口位置脚本设不了（design.md §35.3 不适用）；同时只能有一个 PiP 窗口，打开它的标签页关掉或整页跳转时跟着关；YouTube 快捷键在 PiP 窗口里不起作用，样式表要复制过去；Wayland 下可能不置顶（GNOME 最可疑）。

**真要做时**：先花半天做原型验证 A（切视频、广告、回到观看页、置顶），顺便放一个自己画的列表，看点一条时主页面能不能换视频；A 稳定就用 A，不稳用 B；作为单独一项子开关加到 design.md §34。

**进度**
- 2026-11-20：提出意向，还没实测。

# 新功能

## P13 评论弹幕

> 只是意向，还没讨论细节，也没实测。

**一句话**：把视频的评论做成弹幕，在画面上从右往左飘过。带时间戳的评论在那个时间点出现；赞多的优先显示。

**初步想法**
- **评论从哪来**：跟页面一样调 InnerTube 的 `next`，用评论区的 continuation token 翻页。只读。翻页要有上限（比如前几百条），按需加载。
- **时间戳**：YouTube 已经把评论里的时间戳解析成链接（`commandRuns` / `navigationEndpoint` 里的 `watchEndpoint.startTimeSeconds`），直接用。一条评论有多个时间戳时每个时间点各出现一次（显示附近一段还是整条，待定）。
- **优先级**：同一时间段太多时按赞数排序，其余丢掉；置顶评论、作者回复可以加权。
- **没有时间戳的评论**，待定：① 不显示；② 按赞数挑一部分均匀撒在整个视频上。可能做成设置项。
- **显示**：盖在 `#movie_player` 上的透明层，`pointer-events: none`；控件栏上一个开关按钮。可调密度、透明度、字号、只用上半屏。暂停时停住，拖进度条时重排。全屏、影院模式、迷你播放器（太小时要不要关）都要考虑。
- **回复**：先只用一级评论。
- **不做**：直播和直播回放（已有聊天回放）、Shorts。

**要先想清楚 / 实测的**
1. 带时间戳的评论平均有多少。如果大多只有几条，只放带时间戳的会很冷清，这决定了上面「没有时间戳的评论」选哪个。
2. `next` 默认给「热门评论」，翻页能拿到多少条；赞数字段是「1.2K」这种缩写还是精确数字。
3. 翻评论会不会被限流，要不要像 TL;DR 一样按视频 ID 缓存。
4. 透明层盖上以后，官方的悬停显示控件栏、双击全屏、字幕位置会不会受影响。
5. 跟官方字幕重叠时怎么避让。

**进度**
- 2026-11-20：提出意向。
