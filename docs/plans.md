# TL;DR

## P2 凭证缓存

**现状**：`generate()` 和 `deleteConversation()` 各自先 GET 一次 `/u/N/app`，每批 4 个请求，其中 2 次是抓页面。浪费的是 HTTP 请求，不是 Gemini 额度；但增加延迟，流量也更像机器。

**改法**：
- 把 `at` / `bl` / `sid` 按账号 N 缓存几分钟，改 N 时清掉。
- 遇到 400 / 405 时清缓存、重抓、重试一次；还失败就按现有的错误映射处理。
- 自检和「我已登录」检测（design.md §15.1）仍然实时抓，不走缓存。
- 一起缓存 `processSession` 的 API key `d2zJAe`（同一个页面里，跟登录状态无关，很少变；design.md §10.8）。

跟走哪条通道无关：缓存只管凭证从哪来、什么时候刷新。两条通道和删对话都用这组凭证。

**进度**
- 2026-11-20：定下改法，决定先不做。

## P3 官方 Gemini API Provider

**想要什么**：`StreamGenerate` 下线时 TL;DR 不至于整个失效。

**做法**：实现 `SummaryProvider`（design.md §9.1）。用户在设置里填 AI Studio 的免费 key，直接把 YouTube URL 交给模型。

**好处**：有文档；没有封号风险；不需要 YouTube 应用和活动记录，也不用删对话。
**代价**：用户要自己填 key，不再是零配置，但仍然免费。

**跟网页通道的关系**：原来打算当 `StreamGenerate` 下线时唯一的后备。2026-11-21 `processSession` 已经实现（design.md §10.8），两条网页通道互为后备，这一条往后放。仍然有价值：两条都是内部接口，以后照样可能变；也不受 P15 的个性化设置影响。

**进度**
- 2026-11-21：P4（现 design.md §10.8）原型证明 YouTube 应用在新协议下能用，P3 往后放。
- 2026-11-21：优先级改为看 P4 原型的结果再定。
- 2026-11-20：倾向在 P4 之前做。

## P15 Gemini 的个性化设置污染回答

**现象**（日志，StreamGenerate 时期）：2026-11-20 15:30、20:19 两批，Gemini 用「撒撒」小狗的口吻、称呼用户名字，写了一篇带表情的 markdown 总览，没有按要求只输出 JSON，整批 5 个都算失败。看起来是账号里的个性化设置（保存的信息、自定义指令或个人情境）也作用到了扩展发的请求上。

**要先查的**：是哪一项设置；`processSession` 下是否一样；请求里有没有字段能关掉个性化（网页前端的「临时对话」会不会关掉它，但临时对话用不了 YouTube 应用，design.md §10.6）。

**可能的改法**：prompt 里明确要求忽略人设和保存的信息；回答不是 JSON 时拆成单个重试（同 P16）；实在不行就在设置页和自检里提示用户关掉那项设置。

**进度**
- 2026-11-21：从日志里发现，记下。

## P16 一个视频被拒，整批都失败

**现象**（日志）：2026-11-20 20:21–20:22，连续 3 批回答都是「违反政策」的拒绝，三批里都有 `0rEfO0pShEU`。一个视频被拒，整批 5 个都记成「答案里缺了」的 `transient`；重试时它又被分进下一批，把别的视频一起拖下水。2026-11-20 01:03 还有一批回答「I'm having a hard time fulfilling your request」，可能是同类问题。

**改法**：整批没解析出任何结果时，拆成单个视频重试一次；单个也被拒的视频标成不能总结（不再算 `transient`），不再进批。

**进度**
- 2026-11-21：从日志里发现，记下。

## P17 批量回答像 JSON 却没解析出来

**现象**（日志）：2026-11-21 01:15 一批，回答开头是正常的 JSON 数组（`"id"`、`"status":"ok"` 都在），结果 5 个全记成「答案里缺了」。日志只记了前 500 个字符，看不出是被截断、转义有问题还是后面多了东西。同一批要求中文，`points` 却是英文（`lang` 写的是 `zh`）。

另外 2026-11-20 12:26 有两次 `no answer text in 136 bytes`（`protocol`），也是没留下原文。

**下一步**：解析失败时把完整回答记进日志（只记模型的回答，不记请求），下次出现就能看到原因；再看 `parseBatch` 要不要更宽松。语言不对的问题等有更多例子再看。

**进度**
- 2026-11-21：从日志里发现，记下。

## P11 迷你播放器面板偶尔缺刚加的视频

原 `queue-test-findings.md` 的 F12。

- **场景**：播放列表模式，迷你播放器在放单个视频，点「加入 <列表名>」。
- **预期**：迷你播放器下面出现列表：当前视频 + 列表原有条目 + 刚加的视频（「1 / 4」）。
- **实际**：完整跑一遍 L4 时出现过一次，面板只有「1 / 3」，缺刚加的那个；顶栏数字是对的。单独连跑 6 次都正常。
- **推测原因**：`syncList()` 用 `next` 读列表，读不到新视频时在 1.5、3、5 秒后再读，最后一次不管满不满足都用（design.md §24.8）。如果 `next` 落后超过约 9.5 秒，面板就缺这一条，之后也不会再补。
- **测试**：`queue-panel.spec.ts` › playlist mode, a single video in the miniplayer…；`modes.spec.ts` › ② single video in the miniplayer…（按正确结果断言，偶尔会失败）。
- **如果经常出现**：最后一次读取仍不满足时，过一会儿再补一次 `syncList`；或者等面板派发的 `yt-playlist-data-updated` 再核对一次。

**进度**
- 2026-11-21：L4 里出现一次，先观察。

# 播放器

## P12 迷你播放器弹出到桌面

**想要什么**：迷你播放器能放到整个桌面上随便挪，切到别的标签页或程序时也一直浮在最上面。

**只能用浏览器的画中画（PiP）**，页面里的元素出不了浏览器窗口。可选做法：

| | 做法 | 能放什么 | 问题 |
|---|---|---|---|
| 0 | 视频画中画：`video.requestPictureInPicture()` | 只有画面和浏览器给的简单控件 | YouTube 已经有了，没有新东西 |
| A | Document PiP（`documentPictureInPicture.requestWindow()`），把整个 `#movie_player` 搬进去 | 官方完整控件，design.md §35.1 的改造也跟过去 | YouTube 切换观看页 / 迷你播放器时会把 `#movie_player` 搬回去，跟我们抢；播放器不知道 PiP 窗口的大小 |
| B | Document PiP，只搬 `<video>`，控件自己画 | 画面 + 自己的控件，以后还能放列表面板 | 多写一套控件，但不太跟 YouTube 抢 |

Document PiP 只有桌面版 Chrome/Edge 116+ 支持。把正在播的 `<video>` 搬到另一个文档，播放不会停。

**列表也能放进去**（只限 Document PiP，视频画中画放不了）。PiP 窗口是一个完整的空白网页，什么 DOM 都能放：
- 不搬 YouTube 的列表面板（`ytd-playlist-panel-renderer`）。它的点击、换视频、删除、拖动排序都靠事件冒泡到主页面的 `ytd-app`，搬过去以后事件只冒泡到 PiP 窗口自己的文档，传不过去；样式要整套复制；YouTube 重绘时还会跟我们抢元素。
- 在 PiP 窗口里自己画列表。数据用队列现有的那套（`rpc.ts` 现在就在刷新侧栏和迷你播放器下面的列表），点某一条时交给主页面去换视频。播放器用方案 A 还是 B 都可以这样做。
- 窗口大小由用户拖，脚本只能定初始大小，列表要能跟着窗口高度变，窗口矮时可以收起。

**改不了的限制**：只能由用户点击打开；窗口位置脚本设不了（design.md §35.3 不适用）；同时只能有一个 PiP 窗口，打开它的标签页关掉或整页跳转时跟着关；YouTube 快捷键在 PiP 窗口里不起作用，样式表要复制过去；Wayland 下可能不置顶（GNOME 最可疑）。

**真要做时**：先花半天做原型验证 A（切视频、广告、回到观看页、置顶），顺便放一个自己画的列表，看点一条时主页面能不能换视频；A 稳定就用 A，不稳用 B；作为单独一项子开关加到 design.md §34。

**进度**
- 2026-11-20：提出意向，还没实测。

# 新功能

## P13 评论弹幕

> 只是意向，还没讨论细节，也没实测。

**一句话**：把视频的评论做成弹幕，在画面上从右往左飘过。带时间戳的评论在那个时间点出现；赞多的优先显示。

**初步想法**
- **评论从哪来**：跟页面一样调 InnerTube 的 `next`，用评论区的 continuation token 翻页。只读。翻页要有上限（比如前几百条），按需加载。
- **时间戳**：YouTube 已经把评论里的时间戳解析成链接（`commandRuns` / `navigationEndpoint` 里的 `watchEndpoint.startTimeSeconds`），直接用。一条评论有多个时间戳时每个时间点各出现一次（显示附近一段还是整条，待定）。
- **优先级**：同一时间段太多时按赞数排序，其余丢掉；置顶评论、作者回复可以加权。
- **没有时间戳的评论**，待定：① 不显示；② 按赞数挑一部分均匀撒在整个视频上。可能做成设置项。
- **显示**：盖在 `#movie_player` 上的透明层，`pointer-events: none`；控件栏上一个开关按钮。可调密度、透明度、字号、只用上半屏。暂停时停住，拖进度条时重排。全屏、影院模式、迷你播放器（太小时要不要关）都要考虑。
- **回复**：先只用一级评论。
- **不做**：直播和直播回放（已有聊天回放）、Shorts。

**要先想清楚 / 实测的**
1. 带时间戳的评论平均有多少。如果大多只有几条，只放带时间戳的会很冷清，这决定了上面「没有时间戳的评论」选哪个。
2. `next` 默认给「热门评论」，翻页能拿到多少条；赞数字段是「1.2K」这种缩写还是精确数字。
3. 翻评论会不会被限流，要不要像 TL;DR 一样按视频 ID 缓存。
4. 透明层盖上以后，官方的悬停显示控件栏、双击全屏、字幕位置会不会受影响。
5. 跟官方字幕重叠时怎么避让。

**进度**
- 2026-11-20：提出意向。
